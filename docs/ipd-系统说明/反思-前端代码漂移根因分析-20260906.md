## 一、何为「漂移」（定义）

**漂移** = 同一份业务知识/同一类工程责任，在前端代码库内**多源落点**且**互不感知**的状态。

它**不是 bug**（功能正确），**不是漏洞**（安全无害），**不是性能问题**（不影响首屏）。
它是**「知识负债」**——三个口径都跑得通，但**任何一处的更新都漏改另外两处**，未来 owner 修一处忘两处时漂移就从"并存"变成"行为分歧"。

按严重程度分四级：

| 等级 | 定义 | 本次发现 |
|---|---|---|
| **P0 漂移** | 已导致**类型/接口二义性**——消费者必须二选一；新代码易引错 | 0 |
| **P1 漂移** | 已导致**维护放大**——同一逻辑 4 份拷贝；任一份漂移则后续修改漏接 | 2（错误码/产品组） |
| **P2 漂移** | 已导致**结构不一致**——同类占位该用统一组件但实际散用 | 1（BackendPending） |
| **P3 漂移** | 已导致**未决议的技术债**——happy-dom/dayjs 5 unhandled 已知未修 | 1（fe-detail） |

## 二、具体漂移证据（文件系统级）

### 2.1 【P1】产品组接口二义性 ——`api/ipd/product.ts` vs `api/ipd/product-group.ts`

| 维度 | `product.ts` | `product-group.ts` |
|---|---|---|
| 文件位置 | `src/api/ipd/product.ts` | `src/api/ipd/product-group.ts` |
| 接口名 | `ProductGroup` | `IpdProductGroup`（带 `Ipd` 前缀） |
| 函数名 | `listProductGroups()` | `listProductGroups()` |
| 调用端点 | `/product-groups` | `/product-groups` |
| normalize 函数 | `normalizeGroup` | `normalize` |
| 调用方（grep 结果） | `views/ipd/product/{list,edit}/index.vue` | `views/ipd/admin/org/index.vue` |

**事实**：两份代码指向**同一后端端点**，**同一份数据**，但 TS 类型系统**不互通**——`ProductGroup` 不能直接传给消费 `IpdProductGroup` 的函数。

**谁先写、谁后写**：
- 收口报告第 75 行明确登记："fe-misc 建 `api/ipd/product-group.ts`（admin/org 用），fe-product 在 `api/ipd/product.ts` 内也导出 `listProductGroups` + `ProductGroup`（product/list + product/edit 用）"
- 推断：fe-product（页面 16/17 产品管理）先写，fe-misc（页面 28 组织架构）后写——**两智能体无共享层感知**

### 2.2 【P1】错误码映射四源散落 ——bid/project/ai-document/portal 各一份

| 文件 | 关键导出 | 行数 |
|---|---|---|
| `views/ipd/bid/bid-error.ts` | `bidErrorText`, `isTransportError`, `BID_CODE_TEXTS` | 45 |
| `views/ipd/project/project-error.ts` | `projectErrorText` + 私 `PROJECT_CODE_TEXTS` | 44 |
| `api/ipd/ai-document.ts` | `ipdApiErrorText` 内联 + `IpdRequestError` 抛出 | 153 |
| `api/ipd/portal.ts` | `PORTAL_ERROR_TEXT` 内联 + `IpdRequestError` 抛出 | 216 |

**关键事实**：
- bid-error 与 project-error 都在 `views/ipd/<domain>/` 目录，**实现模式几乎相同**（同样的 `codeTexts` 覆盖 + 同样的 fallback）
- ai-document 与 portal 把错误码映射**直接埋在 api 层**（与请求/响应处理同文件）——这是**违反分层**：错误码→中文文案是**视图关切**，但它现在跟 fetch 混合
- `IpdRequestError`（在 `api/ipd/auth.ts`）是 4 份的**共同基类**——证明四份代码**都知道存在统一的基类**，但**仍各自维护自己的 code→text 表**，没有走"基类提供默认文案 + 视图层只覆盖"

## 三、严重根源性原因（5 层，深度递进）

### 3.1 根因层一：**多智能体并行而无"前端领域架构师"**

8 个 fe-* 智能体（fe-bid/fe-project/fe-misc/fe-product/fe-detail/fe-admin/fe-portal/fe-consistency）**同时**对前端仓做改动，**每个智能体只知道自己的页卡**。

**深层原因**：
- IPD 是"页卡驱动"工作流（每张卡 = 1 张 P0-10.x 前端页），**没有页卡维度**谈"前端共享层"——共享层是横向关切，不属于任何一张页卡
- 任何智能体认领"招标组队"卡时，他的潜意识是"招标组队域完整"，**不是**"全 IPD 域完整"
- 共享层是**系统级抽象**，需要全栈视野——但工作流是**卡级实现**，没有位置放这个角色

**这是组织级 root cause，不是工程级**。修法不是"加测试"，是"在认领阶段就预留共享层位置"。

### 3.2 根因层二：**后端仓与前端仓物理分离导致"接口契约"在两端各做一次**

后端仓：`/Users/mac/Documents/ruoyi-ai`（52 个 controller, 269 DTO）
前端仓：`/Users/mac/Documents/ruoyi-ipd-web`（37 个 .vue, 21 个 .ts api）

**关键现象**：
- 后端定义 `ApiV1ErrorCode`（PARAM_INVALID/UNAUTHORIZED/...）作为**业务错误码权威源**
- 前端 `IpdRequestError` 在 `api/ipd/auth.ts` **重新声明 errorCode**（4 处错误码映射都引此基类）
- 数字码 10001/20001/... 前后端是**字符串匹配**，**不是类型系统联动**

**这意味着**：后端改 `ApiV1ErrorCode.PARAM_INVALID.code` 从 10001 → 10002，**前端四份错误码表全部漏接**。

**深层原因**：
- 后端是 Java，错误码是 enum 强类型
- 前端是 TS，错误码是 `Record<number, string>` 弱类型
- 物理仓隔离 = 没有 `openapi-typescript` 自动生成 = 人工抄码 = 必漏

### 3.3 根因层三：**"二开复用铁律"在共享层定义前就生效**

收口报告第 12 行（交接清单）：「二开复用铁律（owner 20260905）：基于若依基座二开，登录/布局/RBAC/组件/公共模块该复用的复用，禁止另起炉灶重写一套」。

这条铁律**对外**（不复写若依）执行得不错，但**对内**（不在 IPD 内部重复造轮子）**没有**对应的"内部复用铁律"。

**现象佐证**：
- 错误码 4 份 = 没有"前端内部 IPD 错误码中心"约定
- 产品组 2 份 = 没有"产品域只允许在 product.ts"约定
- BackendPending 仅 14% 使用 = 没有"占位必须用 BackendPending"约定

**深层原因**：
- owner 指令"二开复用若依"是**基座级**的，没下沉到**业务域级**
- 业务域级复用需要**前端架构师角色**——而当前模式是"按卡认领"，没有这个角色
- 当卡面 review 只检查"页是否落地 + 路由是否切换 + 测是否绿"，**没有人 review "你有没有复用既有"**——验收口径没有这一栏

### 3.4 根因层四：**"实做落地"质量门 = 功能正确，未含"与既有一致"**

收口报告第 6-15 行登记的集成阶段结果（"31 文件：29 passed / 1 failed / 1 skipped；262 用例：259 passed / 2 failed（98.9% 通过率）"）——**只看测试通过率，不看是否有重复**。

**深层原因**：
- 测试是**功能正确性**的代理指标，不是**架构一致性**的代理指标
- "pass 98.9%"给了 reviewer 强信号"可以收口"，但**测试不验证"你的实现是否和别处实现等价"**
- 一致性需要专门的**架构层断言**（如"产品组接口必须只允许一份"），但项目没有 lint 规则守护

### 3.5 根因层五：**"谁后写谁占主导"的隐式权力规则未被声明**

产品组 2 份就是典型——fe-product 先写，fe-misc 后写，**后写的没回头看有没有现成的**。

**深层原因**：
- 智能体认领卡时只查"接口契约卡"（如 P1-1.2 / P2-1.1 后端接口定义），**不查前端仓**"别人已经写了什么"
- 即便查了，也是按"目录名"查（如 `views/ipd/product/`、`views/ipd/admin/`），**不查 api/ 层跨域定义**
- 缺乏**"认领前先 grep 同名 API"的约定**——这是**过程级**的问题，不是产出级

## 六、本反思的核心结论

> **前端漂移不是"代码烂"，是"工程组织模型"与"代码组织模型"错位。**

- 卡驱动工作流（card-driven）**擅长产出**——8 智能体 12 小时产 35 页
- 卡驱动工作流**不擅长架构**——架构是横向关切，不是任何一张卡的纵向责任
- 35/49 = 71% 实做率证明**产出强**；4 份错误码 + 2 份产品组 + 14% 占位组件使用率证明**架构弱**

**修法不是"再做几遍"**——再做 5 遍仍是同样漂移，因为这是工作流结构性盲区。
**修法是"加横向角色"**——要么显式"前端架构师"智能体，要么在认领阶段强制 grep + 中心化共享层表。

未来 owner 拿到这 35 页实做 + 这份反思，**首要决策**应该是：
1. **是接受漂移**（用 4 份错误码表换 0.5 天开发时间）——可行但要登记技术债
2. **是收口整合**（花 1-2 天统一 4 份 → 1 份）——影响前端 8 智能体后续工作流（先 grep 再写）

本会话作为"产出型"智能体，**只能记录并上报**，**不能跨智能体执行整合**（那是"整合型"角色的责任）。
