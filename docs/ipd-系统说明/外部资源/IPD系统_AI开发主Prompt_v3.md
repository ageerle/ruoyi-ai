## 0. 全局硬约束（最高优先级）

**G-01 业务闭环**：所有流程必须有发起、处理、审核、结果、记录、归档六个环节。禁止存在无出口的流程节点。
**G-02 权限隔离**：三层角色（超级管理员 / 产品组长 / 普通PM）权限严格隔离。编辑可自主，**删除必须走申请审核**，任何人无直接删除权限。
**G-03 审计留痕**：所有新增、编辑、审核、驳回、删除、移交、参数修改、人员同步、登录凭证变更全部写入审计日志。日志只追加、不可修改、不可删除。
**G-04 制度优先**：本文件参数与源需求文档冲突时，**以本文件（对齐 V3.1）为准**。冲突清单见第 9 节。
**G-05 参数可配置**：所有系数、阈值、期限、额度必须落库为后台可配置参数表，**禁止硬编码在业务逻辑中**。
**G-06 无绝对化承诺**：不要生成"100%闭环""无遗留疑问"这类文案。未知状态显式展示为"待补充""未配置"。
**G-07 中文界面**：全中文。所有文案抽离为 i18n 资源文件，数据库文本字段预留多语言 JSONB 扩展位，一期只填 `zh-CN`。
**G-08 涉钱参数必须可切换（虽已裁定，仍禁止硬编码）**：奖金池基数、销售额口径、绩效系数取值、系数定值主体、池分摊方式、上市锚点共 6 项已于 2026-09-02 由 Gavin 裁定（最终值见第 7 节参数表）。**即便已定案，仍必须实现为后台配置开关，切换口径只改配置不改代码**——制度未来可能修订。相关公式一律走参数服务取值，代码中不得出现任何系数、阈值、比例、期限的字面量。
**G-09 角色体系不扩展**：系统只有三个业务角色（普通PM / 产品组长 / 超级管理员）+ 游客。**不新增「评审上级」「代理组长」「代审人」等角色**。V3.1 原文中的"直接上级"在系统内统一映射为**产品组长**。
**G-10 市场PM 视角优先**：本系统的工作重心是市场PM。研发PM 主导阶段（开发/验证）**默认轻管**——界面只保留「完成状态 / 实际完成日期 / 备注」三个字段，禁止做任何过载设计（不加执行记录、不加 SOP 强制展示、不加交付物校验）。仅法规认证类与 Gavin 明确要求保留阻断的动作例外。

### TS-01c 数据库双账号分离（⚠️ 硬约束，2026-09-03 裁定）

**背景**：验收项 **AC-AUD-01** 要求「直接用数据库客户端 UPDATE 审计日志 → 被拒绝」，
依赖 PG 层的 `REVOKE UPDATE, DELETE ON audit_logs`。
而 PostgreSQL **超级用户绕过一切权限检查**——应用若以 `postgres` 连接，该 revoke 完全失效，P0 门必挂。

**因此强制拆成两个账号**：

| 环境变量 | 账号 | 超级用户 | 用途 | 允许出现的位置 |
|---|---|---|---|---|
| `DATABASE_URL` | `ipd_app` | ❌ | 应用运行时全部读写（Prisma Client） | 仅 `schema.prisma` 的 `url`、应用运行配置 |
| `DIRECT_URL` | `postgres` | ✅ | 仅 `prisma migrate` / `db push` / 手工建表 | 仅 `schema.prisma` 的 `directUrl`、迁移脚本 |

**`schema.prisma` 必须写成**：

```prisma
datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")    // ipd_app，运行时
  directUrl = env("DIRECT_URL")      // postgres，仅迁移
}
```

**红线**：
- **G-11 禁止在应用业务代码中引用 `DIRECT_URL`**（包括 seed、脚本、测试之外的任何运行时路径）
- seed 脚本属于运行时数据写入，**用 `DATABASE_URL`（`ipd_app`）执行**，不得走 `DIRECT_URL`
- migration 中 `REVOKE` 语句针对的角色是 `ipd_app`，不是 `postgres`
- 连接串内密码的 `@` 必须 URL 编码为 `%40`（否则 libpq 解析 host 会歧义）

**T-03 迁移中必须包含的 SQL**（针对 `ipd_app`）：

```sql
REVOKE UPDATE, DELETE ON audit_logs FROM ipd_app;
```

验收方式：以 `ipd_app` 身份执行 `UPDATE audit_logs SET ...` 必须被拒绝（AC-AUD-01）。

### TS-03 编码规范

- 前后端全量 TypeScript，**禁止 any**（确需时用 `unknown` + 类型守卫）
- 后端分层：Controller 只做参数校验与转发 → Service 承载业务逻辑 → Prisma 做数据访问。**业务逻辑不得写在 Controller**
- 所有写操作通过 `@Audit()` 装饰器自动记录审计日志（切面实现，不在业务代码里手写日志）
- 所有列表接口支持分页（page/size）+ 排序 + 筛选，返回统一结构 `{ list, total, page, size }`
- 所有接口返回统一包装：`{ code, message, data, timestamp, traceId }`，业务错误码见 TS-09
- 数据库所有表含 `id`(uuid) / `created_at` / `updated_at` / `deleted_at`（软删除）/ `created_by` / `updated_by`
- 金额字段用 `DECIMAL(18,2)`，**禁止用 float**
- 日期字段统一 `TIMESTAMPTZ`，前端展示转本地时区
- 枚举值全部落库为字典表或 PG enum，前端从字典接口取，不硬编码

### TS-07 状态机

- 每条日志计算 `currHash = SHA256(prevHash + JSON(本条内容))`

- 日志表**不开放 UPDATE/DELETE 权限**（PG 层 revoke），仅 INSERT

### 3.0 术语表（开发必须遵守，避免概念混用）

| 术语 | 定义 |
|---|---|
| **产品** | 一个可售卖的产品/产品线，是项目与需求的上层实体。**与项目 1:1**（Q5 决策：一个产品 = 一个项目）。三种来源：在售型号由超管导入 / 在研产品由 PM 登录后新增 / 游客提需求时选「其他」占位 |
| **项目** | 一次具体的研发过程实例，挂在一个产品下（1:1），绑定一对双PM |
| **双PM** | 市场PM + 研发PM 的固定组合，绑定项目全生命周期 |
| **市场PM** | 市场与客户代言人。决策"做什么产品、为哪个场景做、目标客户是谁、何时上市" |
| **研发PM** | 技术与可行性代言人。决策"技术路线、架构设计、创新方向、开发排期" |
| **深管动作** | 市场PM 主责动作，需完整管理（状态/记录/强制交付物/门禁阻断） |
| **轻管动作** | 研发PM 主责动作，仅登记完成状态 + 完成日期 + 备注 |
| **阻断性动作** | 未完成则禁止跳转到下一 IPD 阶段 |
| **直接上级** | ⚠️ **系统中无此角色**。V3.1 原文的"直接上级"在系统内统一映射为**产品组长**（A5/Q4 决策）。三方评定 = 双PM + 各自产品组长 |
| **回款** | ⚠️ 销售达成率的计算口径为**实际回款金额**（Q2 决策）。注意 V3.1 全文无"回款"概念（原文用"实际销售额/出货量"），此为 Gavin 明确的管理决策，制度文本需后续同步修订 |
| **项目绩效综合得分** | 评定对象**不是季度**，而是**该项目从概念阶段到发布阶段的完成情况**（Q3 决策）。功能KPI 60% + 共担KPI 40% |
| **需求** | 来自需求池的外部/内部输入 |
| **需求变更单** | 需求进入项目后触发的变更流程对象，走双签否决 |

### 3.1 组织与权限（BR-ORG）

**BR-ORG-01 跨组组队归属**：项目主组 = 市场PM 所在产品组；协同组 = 研发PM 所在产品组。两组组长均可查看该项目；删除初审由**主组组长**负责，协同组组长自动知会。

**BR-ORG-02 人员归属**：一个产品经理仅归属一个产品组。

**BR-ORG-03 组长兼任与项目数上限（A4 决策）**：产品组长可以同时是项目的市场PM/研发PM，同样受"≥3 项目须评级委员会审批备案"约束（V3.1 §4.2 原文）。**组长自己负责的项目最多 3 个**，但**可以查看本组组员的所有项目**（不含跨组的协同组项目）。

**BR-ORG-04 组长来源（A3 决策）**：产品组长**随第三方 API 同步**——组长角色在 HR（第三方）系统中标注，同步到本系统。**不做代理组长 / 代审人机制**（Gavin 明确不需要）。超管角色（SUPER_ADMIN）由系统初始化内置，不走 API 同步。

**BR-ORG-05 组长可视范围（A2 决策）**：组长可查看**本组 PM 主责或参与的全部项目**，含轻管动作的完成状态（但不强制组长审核附件）。跨组项目（市场PM 在本组、研发PM 在协同组）仅展示本组 PM 相关的部分。

**BR-ORG-06 三层权限矩阵**

| 能力 | 游客 | 普通PM | 产品组长 | 超级管理员 |
|---|---|---|---|---|
| 提交需求 | ✅ | ✅ | ✅ | ✅ |
| 查看项目 | — | 仅本人负责 | 本组全部 | 全部 |
| 编辑项目 | — | 仅本人负责 | 仅本人名下 | 全部 |
| 发起删除申请 | — | ✅ | ✅ | ✅ |
| 删除初审 | — | — | ✅（本组） | — |
| 删除终审 | — | — | — | ✅ |
| 调用 AI | — | ✅ | ✅ | ✅ |
| 配置系统参数 | — | — | — | ✅ |
| 导出审计日志 | — | 仅本人相关 | 本组 | 全局 |
| 人员维护 | — | — | — | ✅ |

**BR-ORG-07 游客权限**：仅可免登录提交需求 + 凭查询码查询进度。无任何审计、查看项目、导出权限。

### 3.2 人员与认证（BR-USER）

**BR-USER-01 人员来源**：市场PM/研发PM **禁止在系统页面手动新增**。数据源为第三方 HR API（一期：本地文件批量导入 + Mock 接口；二期：真实 API）。

**BR-USER-02 同步任务（B6 决策）**：**每月 1 日 02:00** 执行一次定时 check。同步内容按三类处理：
1. **新增人员**：系统内不存在的双PM，自动建档
2. **属性变更**：对已有双PM，逐字段比对，**L1–L5 等级是否更新**是重点比对项；有变化则更新 `level` 与 `levelUpdatedAt`，写审计并生成差异提醒
3. **离职状态**：置 `employmentStatus = RESIGNED`，触发 BR-USER-06 移交流程

同步结果（新增数 / 变更数 / 等级变更明细 / 离职数）写入审计日志，并生成同步报告供超管查看。

**BR-USER-03 同步字段**：姓名、工号、所属产品组、PM 类型（市场PM/研发PM）、**是否为产品组长**（A3 决策：组长角色在第三方系统标注后同步）、L1–L5 等级、在职/离职状态。

**BR-USER-04 登录方式一（账号密码）**：用户名 = 姓名。初始化分配默认密码，**无密码过期时间，但强制首次登录修改默认密码**，未修改前默认密码持续有效。密码修改写审计。

**BR-USER-05 登录方式二（企微扫码）**：一期 Mock（模拟授权页），保留标准 OAuth 接口位。企微账号须与系统内人员绑定后方可登录。

**BR-USER-06 离职与工作调整处理（B8 决策 · 关键闭环）**

⚠️ **顺序已按 Gavin 决策调整：先移交项目，再禁用账号**（v2 的"先冻结再移交"作废）。

完整流程：
1. **触发**：API 同步识别到离职或工作调整
2. **进入待移交冻结态**：`accountStatus = FROZEN_PENDING_HANDOVER`。此状态下账号**仅保留"项目移交"相关权限**，不能做其他任何操作，也不发津贴（见第 5 步）
3. **生成待移交任务**：在该员名下自动生成「待移交任务」，同时推送本人 + 双方产品组长 + 超管（站内信 + 企微）
4. **一键移交**：由本人或产品组长/超管代操作（解决"人已走无法登录移交"的问题），支持单项目/批量移交给新的双PM（见 BR-HAND-01）
5. **移交完成 → 账号禁用**：名下项目全部移交完成后，`accountStatus = DISABLED`，解绑企微，禁止登录。**移交生效日所在月的月初 PM 领取当月全额津贴**（BR-INC-11，E26 决策）
6. **逾期升级**：**15 个自然日**内未完成移交，自动升级超管并每日提醒
7. 全部动作写审计

> **为什么保留冻结态**：Gavin 要求"先移交后禁用"，但实际业务中离职人员可能已无登录条件。冻结态让"移交"这件事在账号禁用前必须完成，同时允许组长/超管代操作，堵住"人走了项目烂尾"的漏洞。

**BR-USER-07 等级维护（B6 决策 · 权威源变更）**

| 规则 | 说明 |
|---|---|
| 权威源 | **第三方 API 为 L1–L5 的唯一权威源**，超管**不可修改个人等级**（v2 的 `MANUAL_OVERRIDE` 机制作废） |
| 首次同步 | 首次 API 同步时系统内无评级，直接以 API 值为准，**超管不可修改** |
| 后续同步 | 每月 1 日同步，比对已有双PM 的等级是否更新，有变则更新 `level` + `levelUpdatedAt`，写审计 |
| 超管可配的是 | 不是个人等级，而是 **「L1–L5 各等级 → 月度津贴额度」的映射表**（BR-INC-02 参数） |
| **额度适用的时点规则** | ⭐ **评级结果更新前已挂载的项目，继续沿用原等级的津贴额度；评级结果更新后新挂载的项目，采用新等级的津贴额度**（B6 决策原文）。实现：津贴额度在 `ProjectMember.lockedAmount` 中按绑定时评级快照锁定，见 BR-INC-02 |

**BR-USER-08 角色固定（B7 决策）**：市场PM 与研发PM 的角色**固定不变**，不允许同一人在项目甲做市场PM、项目乙做研发PM。角色由 API 同步值决定，**不提供跨角色授权入口**（v2 的"超管逐项目授权"机制作废）。
**BR-USER-08b 项目内角色互斥**：同一项目内市场PM 不可兼任研发PM（BR-TEAM-08）。

**BR-USER-09 游客查询码**：需求提交成功生成 8 位查询码，游客凭码在门户查询处理进度与结果（不登录、不可改）。

### 3.3 产品与项目（BR-PROD）

**BR-PROD-01 产品主数据（G31 决策 · 三路来源）**

产品是项目与需求的上层实体，**与项目 1:1**（Q5 决策：一个产品 = 一个项目，不做多项目奖金池分摊）。需求挂在产品上，**按产品的负责双PM 自动路由**（这是源文档需求自动通知规则的实现前提）。

| 来源 | 适用场景 | 操作人 | 说明 |
|---|---|---|---|
| ① **超管预先导入** | **在售产品** | 超级管理员 | 系统上线时批量导入在售产品型号库，后续新增在售型号由超管维护 |
| ② **PM 自行新增** | **在研产品** | 登录后的产品经理 | PM 在系统内自行添加在研产品，并可在其下提交产品需求 |
| ③ **游客「其他」占位** | 型号不明确的需求 | 游客（免登录） | 游客选择「其他/不确定」+ 手工填写产品需求信息文本 → 进入需求池 → 由 PM 人工识别归属产品后路由 |

- 第 ③ 类需求进入需求池后状态为「待指派」，PM 认领时绑定到具体产品；长期未指派的由产品组长兜底处理
- 产品编码唯一，产品名支持型号 + 别称
- 产品的负责双PM 从所挂项目自动继承（1:1 关系）

**BR-PROD-02 项目模板**：新建项目选择模板类型（硬件 / 软件 / 解决方案），自动挂载对应动作清单。

**BR-PROD-03 存量导入**：有权限人员导入在研项目 → 补录当前 IPD 阶段、历史资料、指定双PM → 接入完整流程。已过节点标记「历史缺失」并允许上传替代佐证，缺失项在审计日志中标记，**不阻断后续流程**。

**BR-PROD-04 在研项目适配（V3.1 §5.4）**
- 决策权：已过节点不追溯，未过节点双PM 接管
- 三个立即生效切入点：需求变更双签、上市节奏决策、上市后联合复盘
- 市场PM 补入后 **2 周内**必须完成「场景定义复核」，系统自动生成待办并倒计时；发现偏差走需求变更流程
- 功能KPI 补入前不追溯，补入后全量考核
- **共担市场结果 KPI 不分段、不打折，全量共担**
- 月度津贴从双PM 补入**次月**起按评级固定额发放
- 成功奖金与新建项目同一公式

**BR-PROD-05 项目归档**：生命周期阶段标记停产后归档，归档后仅允许查看、导出全部资料，禁止编辑、新增、修改、删除。

| **D11 / Z01** | BioCV 算法训练与评测 | 开发 | **轻** | 研发PM | 不传附件，但**必须登记实测 FAR / FRR 数值** |
| **V10 / Z02** | 跨人种 / 跨年龄适配验证 | 验证 | 深 | 市场PM | 强制上传分人群测试报告。**Z08 算法公平性偏见测试并入本动作 SOP**，不独立编号 |
| **V11 / Z04** | 平台兼容性与 SDK/API 对接验证 | 验证 | **轻**（解决方案模板下自动转**深**） | 研发PM | 仅登记对接范围与通过结论 |
| **V12 / Z05** | 海外市场本地化适配验证 | 验证 | 深 | 市场PM | 强制上传本地化验收清单（逐项打勾） |

**v3 不做的 3 项**（补漏表决策 C）：Z06 BCI 伦理与器械合规审查（本期不做）、Z07 海外制造与供应链本地化评估（本期不做）、Z10 渠道样机/Demo 机发放回收管理（属售后/渠道系统，不做）。

**v3 深度调整**：
- **C10 知识产权与合规预检：轻管 → 深管**（Z09 专利 FTO 分析并入），强制上传检索报告，**但设为非阻断**（重要但不该卡住流程，改为强制留痕 + 逾期提醒）
- **C05 技术可行性预研：维持轻管**（M2 决策"继续轻管"，不做条件升级）

**BR-IPD-03 深管动作（市场PM 主导，42 个）**
- 状态流转：未开始 → 进行中 → 已完成 / 延期
- 强制上传至少 1 个交付物方可标记"已完成"
- 强制展示绑定的 SOP 富文本
- 阻断性动作未完成则禁止跳阶
- 到期前 3 天 / 逾期每天提醒主责人

> 深管集中在市场PM 主战场：概念 11 + 计划 4 + 发布 7 + 生命周期 8 + KPI 归集 4 = **34 个**，占深管总数 81%。

**BR-IPD-04 轻管动作（研发PM 主导，27 个）— 界面只保留三字段**
- 完成状态（未开始 / 进行中 / 已完成 / 不适用）
- 实际完成日期（状态为"已完成"时必填）
- 备注（≤200 字，选填）
- **禁止实现**：强制交付物上传、强制 SOP 展示、执行记录富文本、阶段门禁阻断
- **附件上传入口不提供**（Gavin 已确认：轻管动作无附件上传）

**BR-IPD-05 轻管的三个例外**
1. **法规认证类**（P10 认证规划、V02 认证送检）保留阻断性——认证缺失产品无法上市销售。同样不强制上传证书扫描件，只需登记「已通过 + 通过日期 + 证书编号（文本）」
2. **D11 / Z01 BioCV 算法评测**必须登记实测 FAR / FRR 两个数值字段（熵基技术底盘的最小可见性要求）
3. **V11 / Z04 平台兼容性验证**在「解决方案」模板下自动升级为深管（集成方案是交付主体），硬件/软件模板下维持轻管

**BR-IPD-05b 国别认证清单模板库（M1 决策）**：P10 / V02 的认证项**不得写死**为固定的 5 项。系统内置**国别认证清单模板库**（`cert_templates`），项目选定目标市场（`targetMarkets`）后自动带出对应认证项，并允许手工补充其他项。内置常用项：

| 区域 | 认证项 |
|---|---|
| 欧盟 | CE、RoHS、REACH、GDPR（生物特征数据处理合规） |
| 北美 | FCC、UL/ETL、加州 Prop 65 |
| 中国 | CCC、SRRC、等保 2.0、个保法合规 |
| 中东 | 沙特 SABER/SASO、阿联酋 ECAS/EQM |
| 拉美 | 巴西 ANATEL、墨西哥 NOM |
| 亚太 | 印度 BIS、韩国 KC、日本 PSE/MIC、澳洲 RCM |
| 通用 | CB Scheme、IEC 62443（工控安全） |

超管可后台维护模板库（增删改认证项、调整国别映射）。

**BR-IPD-06 阶段门禁**：当前阶段阻断性动作未完成 → 禁止跳转下一阶段。阻断分级：S 级全阻断（38 个）、A 级约 25 个、B 级约 14 个（仅 Gate 关联动作 + P10/V02 认证 + C12 生物特征合规）。分级规则后台可配置。
**三个"深管但不阻断"的刻意设计**：C10 知识产权预检、V11 平台兼容性（硬件/软件模板下）、LC05 客户反馈处理——重要但不卡流程，改为强制留痕 + 逾期提醒。

**BR-IPD-07 SOP 绑定**：每个深管动作绑定一份 SOP（富文本 + 附件上传入口），支持超管后台编辑，修改后新项目用新版本，在研项目保持原版本。

**BR-IPD-08 上市日期（关键锚点）**：发布阶段 L08 动作录入的 `launchDate` 是全部后置指标的起算原点——6 个月销售/回款统计窗口、90 天复盘、共担 KPI 评估。**该字段录入后不可随意修改，修改需双签 + 审计。**

**BR-IPD-09 阶段视图**：提供可视化流程视图（横向阶段条 + 动作清单），深管动作与轻管动作**视觉上必须可区分**（深管卡片式带交付物图标，轻管行式仅显示状态与日期）。

### 3.5 双PM 组队与招标（BR-TEAM）

**BR-TEAM-01 招标发起**：市场PM 发起新项目 → 发起研发PM 招标。两种模式：
- ① 一对一邀标：定向邀标指定研发PM，**仅限被邀本人应标，不可转发**
- ② 公开招标：面向全部研发PM

**BR-TEAM-02 招标有效期**：每个项目独立设置有效期。市场PM 可在有效期内修改招标条件、手动关闭招标单，操作写审计。

**BR-TEAM-03 拒绝应标**：研发PM 可拒绝应标，**拒绝行为不留系统痕迹**（不记录、不通知）。

**BR-TEAM-04 邀标转公开**：一对一邀标被拒后，市场PM 可手动改为公开招标，操作写审计。

**BR-TEAM-05 遴选与通知**：研发PM 应标后由市场PM 最终遴选。遴选完成须向**未中标者**发送站内信 + 企微通知告知结果，通知记录留痕。

**BR-TEAM-06 到期未遴选**：到期前 3 天提醒市场PM；到期自动进入「待遴选」挂起；挂起 7 日未操作，升级至其产品组长提醒。

**BR-TEAM-07 无人应标**：招标单自动关闭，项目转「待组队」挂起，允许市场PM 无限次重新发起；**挂起超 30 日，超管可直接指派研发PM**，指派记录写审计。

**BR-TEAM-08 角色互斥**：市场PM 不允许兼任本项目的研发PM。

**BR-TEAM-09 项目数校验**：同一 PM 绑定项目数 ≥ 3 时弹窗校验，须录入评级委员会审批备案记录，否则禁止绑定第 3 个及以上项目。

**BR-TEAM-10 组队完成**：确定双PM 后生成项目，自动挂载完整 IPD 流程与 Gate 机制，记录评级快照。

### 3.6 五大 Gate 与双签（BR-GATE）

**BR-GATE-01 五大联合 Gate**

| Gate | 名称 | 所在阶段 | 双签否决 |
|---|---|---|---|
| G1 | 立项 Go/No-Go | 概念阶段末（C11） | ✅ |
| G2 | 差异化确认 | 计划阶段末（P13） | — |
| G3 | 开发双周评审 | 开发阶段（D05，每两周） | — |
| G4 | GTM 就绪 | 发布阶段（L07） | — |
| G5 | 上市后 90 天复盘 | 生命周期（LC02） | ✅ |

**BR-GATE-01b 评审要素（v3 新增 · 骨架级内容）**：每个 Gate 具体评审什么，见配套文件 `IPD系统_五大Gate评审要素_v1.md`——G1 七项 / G2 六项 / G3 五项 / G4 八项 / G5 七项，共 **33 项评审要素、14 项否决项**。该文件是本节的详细展开，两者冲突时**以评审要素文件为准**。

实现要求：
1. 33 项要素 seed 进 `gate_review_elements` 表，超管可增删改（要素名称、通过标准、是否否决项、适用 Gate）
2. **判定三态**：✅ 通过 / ⚠️ 带条件通过（须登记责任人 + 关闭期限，否则无法提交）/ ❌ 不通过
3. **否决项硬阻断**：命中任一 ❌ 项，系统不允许提交通过结论，UI 明确提示命中项
4. **遗留项跟踪**：⚠️ 项自动生成待办，关闭前不允许进入再下一个 Gate；逾期未关闭升级产品组长
5. 每次评审生成 `gate_element_results` 记录，与会议纪要一并进入项目档案，永久归档

**BR-GATE-02 强制附件**：Gate 评审附件（会议纪要、评审材料、**评审要素逐项判定表**）为强制交付物，未上传则 Gate 无法闭环。

**BR-GATE-03 双签否决范围**：立项 Go/No-Go（G1）、需求变更审批、上市后复盘（G5）三项执行双签否决，任一方否决即驳回。其余按 RACI 分工，一方主导、一方参与咨询或知会备案。

**BR-GATE-04 并行签署与超时（D17 决策）**：双签**并行**——双方独立提交，在双方都提交前**互不可见对方结论**。签署期限 **3 个自然日**（`gate.signDeadlineDays = 3`，后台可配），到期前 1 天提醒；超期视为**弃权**，按主导方意见执行并记入审计日志。超管可单独延长某个 Gate 的期限，最多 3 次。

**BR-GATE-05 否决后重新发起**：否决后需手动重新发起评审，**不限次数**；但第 3 轮起需双方产品组长列席。

**BR-GATE-06 冲突仲裁**：双PM 意见冲突无法一致 → 升级双方各自产品组长仲裁 → **两组仍不一致则升级超级管理员终裁**。仲裁/终裁结果写入项目审计日志永久归档。

**BR-GATE-07 需求变更路径**：需求池需求经 PM 评估 → 生成《需求变更单》→ 关联项目与 IPD 节点 → 走双签否决 → 通过后回写需求池状态为「已采纳」。**未闭环的变更单阻断所在阶段出口。**

### 3.7 项目移交（BR-HAND）

**BR-HAND-01 移交范围**：支持单项目 / 批量一键移交，支持市场PM、研发PM 独立移交或同时移交。

**BR-HAND-02 数据跟随**：移交后全部历史审批记录、Gate 评审记录、决策日志、文档资料、奖金池台账完整跟随项目移交至新PM。新PM 继承全部权限，接续推进未完成流程。

**BR-HAND-03 津贴与奖金处理（V3.1 §4.2 / §5.4）**
- 月度津贴跟随新接手PM，**按接手时该PM 自身等级锁定额度**；已过去阶段不追溯重算
- 在研项目额度锁定不变，期间原PM 升级不上调
- 奖金池沿用项目立项既定规则，系统支持人工补充登记特殊分配备注，留痕归档

**BR-HAND-04 审计**：全程生成审计日志永久留存。

### 3.8 KPI 考核（BR-KPI）— 源文档遗漏，V3.1 要求，必须实现

> **为什么必须有这个模块**：源文档多处引用"当月综合考核分数 <60 分停发津贴""个人绩效系数"，但源文档只做了津贴与奖金台账，**没有打分体系**。V3.1 §3 定义了完整 KPI 结构，是这两个数值的唯一来源。

**BR-KPI-01 考核结构**：功能KPI **60%** + 共担市场结果 KPI **40%**。共担比例不可低于 30%。

**BR-KPI-02 市场PM 功能KPI（60%，四项各 15%）**

| 指标 | 操作化定义 | 达标线 |
|---|---|---|
| 需求准确率 | 上市后需求变更率 = 变更单数 ÷ 总需求数 | ≤ 15% |
| 市场窗口命中率 | 实际上市时间 vs 计划窗口偏差 | ≤ 30 天 |
| 场景方案竞争力 | 上市后客户验证 + 竞品对比打分 | 评分制 |
| 竞品情报质量 | 情报覆盖度与时效性 | 评分制 |

**BR-KPI-03 研发PM 功能KPI（60%，四项各 15%）**

| 指标 | 操作化定义 | 达标线 |
|---|---|---|
| 上市准时率 | 实际交付 vs 承诺时间偏差 | ≤ 15 天 |
| 质量缺陷率 | PPM | 达标制 |
| 技术创新度 | 差异化专利/方案/架构创新数量与质量 | 评分制 |
| 需求一次性实现率 | 开发过程需求返工率 | ≤ 20% |

**BR-KPI-04 共担市场结果 KPI（40%，双PM 同分同担）**

| 指标 | 权重 | 定义 | 数据来源 | 评分规则 |
|---|---|---|---|---|
| 销量/出货量达成率 | 15% | 上市后 6 个月实际销售额 ÷ 立项目标销售额 | 财务/ERP 出库数据（一期手动录入+凭证） | ≥100% 满分，每低 5 个百分点扣 1 分，<50% 计 0 分 |
| 渠道商覆盖达成率 | 10% | 实际签约渠道/集成商数 ÷ 立项目标渠道商数 | 渠道签约台账 / CRM（一期手动） | 达标满分，每低 5 个百分点扣 1 分 |
| 客户 NPS | 10% | 净推荐值 = 推荐者占比 − 贬损者占比（9-10 推荐者 / 7-8 中立 / 0-6 贬损） | 问卷调研，有效样本 ≥ 30 份 | 达标满分，每低 5 分扣 1 分 |
| 场景覆盖率 | 5% | 实际落地场景数 ÷ 立项规划场景数 | 销售报备 + 交付验收记录 | 按覆盖率比例计分 |

**BR-KPI-05 归集节奏（I5 决策）**：四项共担指标**由产品组长负责录入与复核**（V3.1 原文"产品共享中心按月归集"在系统内落地为产品组长）。

| 归集项 | 责任人 | 频率 | 截止时点 |
|---|---|---|---|
| K01 销量/出货量达成率 | **产品组长** | 月度 | **次月第 5 个工作日 18:00 前**（`kpi.monthlyDeadlineDay = 5`，可配） |
| K02 渠道商覆盖达成率 | **产品组长** | 上市后 6 个月末 | 终算前完成 |
| K03 客户 NPS | **产品组长** | 上市后 6 个月内一次 | 终算前完成，有效样本 ≥ 30 |
| K04 场景覆盖率 | **产品组长** | 上市后 6 个月末 | 终算前完成 |

- 按**月归集、季度对账、上市后 6 个月终算**
- 逾期未归集：第 1 天提醒产品组长，第 3 天升级超管，写审计

> ✅ **截止时点已确认（2026-09-03）**：V3.1 未规定"每月几号前"，采纳建议值 **次月第 5 个工作日 18:00**。仍做成参数 `kpi.monthlyDeadlineDay`，后续可直接改。

**BR-KPI-06 综合得分计算**：`综合得分 = 功能KPI 得分 × 60% + 共担KPI 得分 × 40%`。得分用于绩效系数映射与 <60 分判定。

**BR-KPI-07 在研项目分段**：功能KPI 补入前不追溯、补入后全量考核；共担 KPI **不分段、不打折，全量共担**。

**BR-KPI-08 项目绩效综合得分评定（Q3 决策 · 口径重大变更）**

⚠️ **Q3 决策原文**："这个绩效系数是评估**这个项目从概念阶段到发布阶段**的完成情况"。

| 项 | 口径 |
|---|---|
| 评定对象 | **项目**（不是季度、不是人） |
| 评估区间 | **概念阶段 → 发布阶段**（不含生命周期阶段的上市后表现；共担KPI 按实际归集值计算） |
| 评定时点 | **上市（L08）后 30 日内**完成评定，最迟不晚于 G5 上市后 90 天复盘 |
| 评定人（A5 决策） | **双PM 自评 + 各自产品组长评定**。系统不设技术委员会角色 |
| **权重（✅ 已确认）** | 自评 **20%** + 市场侧产品组长 **40%** + 研发侧产品组长 **40%**，三者之和恒为 100%（前端联动校验） |
| 权重来源说明 | V3.1 §5.2 原文为"自评 20% + 直接上级 30% + 技术委员会 50%"。因 A5 决策取消「评审上级」角色且系统内无委员会实体，将后两项（30%+50%）合并归入各自产品组长。✅ **Gavin 2026-09-03 确认采纳**，落为参数 `kpi.reviewWeights` |
| 评定组成 | 市场PM 得分 = 自评×20% + **市场侧组长**评×40% + **研发侧组长**评×40%；研发PM 同理。即两个组长各自对双PM 都打分 |
| 输出 | 项目绩效综合得分（0–100），用于 BR-INC-07 绩效系数映射 |

> **与 L1–L5 能力等级严格区分**（易混淆，开发必须分清）：
> - **L1–L5 能力等级** = 人，来源第三方 API，每月同步，超管不可改，决定**月度津贴额度**（BR-USER-07）
> - **项目绩效综合得分** = 项目，来源本模块评定，决定**成功奖金的绩效系数**（本条）
>
> 两者不互相推导。一个人可以是 L4（高能力）但某项目绩效得分 65（低产出），津贴照发、奖金按 0.6 系数。

### 3.9 双轨激励（BR-INC）

**BR-INC-01 双轨独立**：月度津贴（评级固定制，保底线）+ 成功奖金（5% 奖金池，盯结果）。两轨独立运作，考核同一套体系。

**BR-INC-02 月度津贴标准与锁定**

| 级别 | 职级名称 | 月度津贴 |
|---|---|---|
| L5 | 首席产品经理 | ¥3,000 |
| L4 | 高级产品经理 | ¥2,500 |
| L3 | 产品经理 | ¥2,000 |
| L2 | 初级产品经理 | ¥1,500 |
| L1 | 助理产品经理 | ¥1,000 |

- **评级锁定**：额度随项目启动时评级锁定，期间升级不上调该项目额度；新项目按最新评级执行
- **不乘绩效系数**
- 当月综合考核 < 60 分 → 当月停发
- 准入：经评级委员会评定级别，从评定通过**次月**起享受津贴

**BR-INC-03 多项目叠加与封顶**：各项目津贴按各自评级额度**全额叠加**（不设边际折扣）；月津贴总额 ≤ 个人当前评级额度的 **2 倍**封顶，超限按 2 倍发放。

**BR-INC-04 奖金池计算（✅ 2026-09-06 owner 裁决改口径：基数 = 实际回款）**

```
奖金池 = 上市后 6 个月实际回款金额 × 5% × 差异化系数
```

**口径变化（2026-09-06 owner 裁决）**：原 V3.1 §4.1/§4.3 主张"目标销售额为基数"（Q1 决策）被推翻——**新口径以实际回款为基数**（与源需求文档原文「实际回款金额 × 5%」一致，也与达成率按回款计算的口径统一）。这意味着超额完成可获得更多奖金池（目标 500 万实回 1500 万 → 奖金池按 75 万基础计算，再经达成率阶梯系数 1.2 调节）。**C08 录入的目标销售额降为达成率分母**而非奖金池基数。

即：
- **奖金池基数 = 实际回款**（LC01 回款台账归集，6 个月终算时锁定）
- **达成率分母 = 目标销售额**（C08 动作录入，G1 通过后锁定；用于"达成率阶梯系数"匹配）
- 二者**不混用**——分母管达成率，分子管基数；详见 BR-INC-04b 注释

> **V3.1 内部口径不一致（已裁定）**：
> - §4.1："前 6 个月**目标**销售额 × 5% × 差异化系数"
> - §4.3 算例："以**目标**销售 ¥500 万为例 → ¥500万 × 5% × 1.5~2.0 = ¥37.5万~¥50万" ← **唯一有算例**
> - §5.5 速查："前 6 个月销售额 × 5% × 差异化系数"（无"目标"二字）
>
> **裁决历史**：① 2026-09-02 Q1 决策采纳 V3.1 目标销售额口径；② 2026-09-06 owner 裁决改回源文档"实际回款"口径——理由是分母目标已用于达成率，无需在基数上重复，**基数=回款可让超额完成获得更多激励**，符合"多劳多得"原则。
> **开发要求**：基数口径必须做成配置开关 `bonus.poolBase = ACTUAL_RECEIPTS`（当前）| `TARGET_SALES`（已废但保留可回退），**禁止硬编码**。目标销售额字段保留在项目档案供达成率计算。
> **参数对照**：`bonus.poolBase` 默认 `ACTUAL_RECEIPTS`；`bonus.achievementTiers` 6 档区间制；`bonus.coefficient.{S,A,B}` = `{1.5, 1.0, 0.8}`。

**BR-INC-04b 达成率的统计口径（Q2 决策：按回款计算）**

```
达成率 = 上市后 6 个月内实际回款金额 ÷ 立项目标销售额 × 100%
```

**回款统计口径定义**（V3.1 未定义，本文件补齐）：

| 项 | 口径 |
|---|---|
| 统计区间 | 上市日期（L08）起 **6 个自然月**（`bonus.monthsWindow = 6`，可配） |
| 统计对象 | 该项目产品在该区间内**实际到账的回款金额** |
| 数据来源 | **一期**：手动录入 + 凭证附件（银行回单/对账单）上传；**二期**：对接 ERP/财务系统回款模块 |
| 归集频率 | 按月录入（LC01 月度台账），6 个月末终算（LC03） |
| 跨期处理 | 区间内下单、区间后回款的部分**不计入**；区间前预收、区间内发货确认的部分**计入** |
| 退款处理 | 区间内发生的退款**当期冲减**；区间结束后发生的退款不回溯（BR-INC-14） |

> ⚠️ **重要提示（需你后续处理）**：V3.1 **全文"回款"出现 0 次**（§3.3 用词为"实际销售额/出货量"）。Q2 决策"按回款计算"是 Gavin 明确的管理决策，**与制度文本不一致**。系统按回款实现，但**建议同步修订 V3.1 文本**，否则制度与系统口径长期背离，后续审计与争议无据可依。
>
> **与源需求文档的关系**：源文档原文就是"实际回款金额"，Q2 决策实际上是**回到源需求文档的口径、推翻我此前的"回款口径作废"建议**。此前结论作废。

**BR-INC-05 差异化系数（E21 决策：已定固定值）**

| 项目等级 | **最终系数** | V3.1 允许区间 | 适用范围 |
|---|---|---|---|
| S 级 | **1.5** | 1.5 – 2.0 | 新场景方案、新技术方向、沙特基地首发产品 |

**BR-INC-06 销售达成率阶梯（✅ 6 档区间制，边界已裁定）**

| 达成率区间 | 阶梯系数 | 判定 | 发放 |
|---|---|---|---|
| **> 120%** | **1.2** | 大幅超额 | 奖金池 × 1.2 |
| **100% – 120%（含）** | **1.0** | 产品成功 | 奖金池 × 1.0 |
| 85% – 99.99% | 0.8 | 基本成功 | 奖金池 × 0.8 |
| 70% – 84.99% | 0.6 | 部分达成 | 奖金池 × 0.6 |
| 50% – 69.99% | 0.3 | 未达成 | 奖金池 × 0.3，触发复盘检讨 |
| < 50% | 0 | 产品失败 | 不发放；月度津贴已发不追回 |

> ✅ **边界裁定（Gavin 2026-09-03 确认）**：采纳区间写法，**取消"=100%"的等值判定与浮点容差**。
> - 100%–120% **闭区间**（含 100%、含 120%）→ 1.0；**> 120%** → 1.2
> - 其余档位下界含、上界不含（左闭右开），如 85% ≤ r < 100% 为 0.8 档
> - 解决了"刚好 100.4% 反而掉档"的怪现象，也消除了浮点边界问题
> - 参数 `bonus.equalityTolerance` **作废删除**，代码中不得出现等值判定逻辑
> - **开发要求**：阶梯用区间匹配实现（按达成率从高到低逐档匹配），**禁止用 `===` 或浮点容差判定**

**BR-INC-08 成功奖金公式**

```
每人成功奖金 = 奖金池 × 达成率阶梯系数 × 贡献度比例 × 绩效系数
```

**BR-INC-09 贡献度评定（五维度）**

| 维度 | 权重 | 偏市场PM 依据 | 偏研发PM 依据 |
|---|---|---|---|
| 立项主导贡献 | 25% | 市场洞察驱动立项、场景定义领先 | 技术前瞻驱动立项、创新方向引领 |
| 差异化创新贡献 | 25% | 提出差异化方向、竞品对标精准 | 技术突破实现差异化、专利产出 |
| 上市节奏把控 | 20% | 窗口判断准、GTM 推动有力 | 交付提速显著、质量稳定 |
| 市场结果贡献 | 20% | 渠道赋能、场景拓展贡献大 | 技术稳定性支撑客户口碑 |
| 协同领导力 | 10% | 主动拉通研发、推动决策 | 主动拉通市场、技术透明 |

- 市场PM 浮动区间 **40% – 65%**，研发PM **35% – 60%**，**两者之和恒为 100%**（前端联动校验）
- 由**双PM + 各自产品组长**在**上市后 90 天复盘（G5）**时联合评定（A5 决策：直接上级 = 产品组长，系统内无「评审上级」角色）
- 按贡献分，不按职位分

**BR-INC-11 停发规则（⚠️ 采用 V3.1 口径）**：附加项目连续 **2 个月无实质产出** → **停发该项目津贴**。

> **与源需求文档冲突**：源文档写"仅提醒，不自动停发"，V3.1 §4.2 明确"停发该项目津贴"。**以 V3.1 为准**。

**BR-INC-12 退出机制**：调离双PM 项目 / 主动退出 / 连续两期考核 < 60 分 → 从**退出次月**停发津贴，**同时放弃成功奖金资格**（`bonusEligible = false`）。

**BR-INC-13 升降级**：升级后新项目按新级别、在研项目额度锁定不变；常规降级新项目按新级别、在研不变；**重大失误即时降级：次月起按新级别执行**。

**BR-INC-14 退款不回溯**：上市 6 个月结束后发生的退款，不做奖金回溯扣减（该场景不处理）。

**BR-INC-15 台账定位**：系统只输出津贴台账与奖金台账记录，**不生成财务正式结算单据**，不对接薪资系统。支持报表导出归档。

**BR-AUD-03 分层导出**：普通PM 仅本人相关 / 产品组长本组 / 超管全局。**游客无审计权限**。

**BR-AUD-04 留存**：默认永久保留，超管可配置归档策略（如 3 年后转冷存储）。

### 3.14 超级管理员移交（BR-ADM）

**BR-ADM-01 超管权限**：系统参数配置、AI 模型配置、组织架构管理、账号权限开通、L1–L5 等级与津贴配置、重大删除终审、全局数据管理。独立账号，不使用 PM 姓名作为用户名。

**BR-ADM-02 移交闭环**：内置「超管权限一键移交」，将全部最高权限、后台配置、AI 配置、审核权限、数据管理权限完整迁移至新超管账号。需二次确认，全程日志留痕。

**BR-ADM-03 移交后**：旧超管账号**禁止登录、作废不可使用**。系统保留完整移交记录，新超管可查看历史移交信息与原超管身份。

**P3 验证**（⚠️ 本阶段公式风险最高，必须先手工核对再往下走）：
- 录入 KPI 打分 → 综合得分正确 → 津贴台账叠加与封顶正确

  → 奖金池 = 450万 × 5% × 1.5 = **33.75 万**；阶梯（85–99.99%）→ 0.8；市场PM = 33.75万 × 0.8 × 55% × 0.8 = **11.88 万**；研发PM = 33.75万 × 0.8 × 45% × 0.8 = **9.72 万**
- **算例 B（验证 1.2 档）**：达成率 130% → 阶梯 1.2；市场PM = 37.5万 × 1.2 × 55% × 1.0 = **24.75 万**
- **算例 C（验证回款口径）**：目标 500 万、区间内回款 350 万 → 达成率 70% → 阶梯 0.6
- **算例 D（验证 120% 端点，2026-09-03 新增）**：
  - 达成率 **120%** → 阶梯 **1.0**（上端点含在内）→ 市场PM = 37.5万 × 1.0 × 55% × 1.0 = **20.625 万**
  - 达成率 **120.1%** → 阶梯 **1.2** → 市场PM = 37.5万 × 1.2 × 55% × 1.0 = **24.75 万**
  - 达成率 **99.99%** → 阶梯 **0.8** → 校验 1.0 档下界为 100%（不含 99.99%）
- 负反馈主责停发连带减半 → 报表可导出
- **静态检查**：代码库中检索 `equalityTolerance`、`=== 100`、`toFixed(2) == ` 应为 **0 命中**
