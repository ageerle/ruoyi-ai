## 2. 十一条全局硬约束（违反即返工，原文摘录）

- **G-01 业务闭环**：所有流程必须有发起、处理、审核、结果、记录、归档六环节。禁止无出口的流程节点。
- **G-02 权限隔离**：三层角色（超管 / 产品组长 / 普通PM）严格隔离。编辑可自主，**删除必须走申请审核**，任何人无直接删除权限。
- **G-03 审计留痕**：新增、编辑、审核、驳回、删除、移交、参数修改、人员同步、登录凭证变更全部写审计。日志只追加、不可改、不可删（PG 层 revoke UPDATE/DELETE）。
- **G-04 制度优先**：本规则与主 Prompt 冲突时，**以主 Prompt v3 为准**（已对齐《双PM绩效考核制度 V3.1》）。
- **G-05 参数可配置**：所有系数、阈值、期限、额度落库为参数表，**禁止硬编码**。
- **G-06 无绝对化承诺**：禁止生成"100%闭环""无遗留疑问"文案。未知状态显式展示为"待补充""未配置"。
- **G-07 中文界面**：全中文，文案抽离 i18n，数据库文本字段预留多语言 JSONB 扩展位，一期只填 `zh-CN`。
- **G-08 涉钱参数必须可切换**：奖金池基数、销售额口径、绩效系数取值、系数定值主体、池分摊方式、上市锚点共 6 项**虽已裁定，仍必须实现为配置开关**。代码不得出现任何系数/阈值/比例/期限的字面量。
- **G-09 角色体系不扩展**：只有三个业务角色 + 游客。不新增「评审上级」「代理组长」「代审人」。V3.1 的"直接上级"统一映射为**产品组长**。
- **G-10 市场PM 视角优先**：研发PM 主导阶段（开发/验证）**默认轻管**——界面只保留「完成状态 / 实际完成日期 / 备注」三字段。禁止加执行记录、SOP 强制展示、交付物校验。仅法规认证类与明确要求保留阻断的动作例外。
- **G-11 数据库双账号分离**：`DATABASE_URL` 用 `ipd_app`（**非超级用户**，运行时读写）；`DIRECT_URL` 用 `postgres`（**超级用户**，仅 `prisma migrate`/`db push`）。**严禁在应用业务代码、seed、任何运行时路径引用 `DIRECT_URL`**。原因：超级用户绕过一切权限检查，若运行时用它，审计表的 PG 层 `REVOKE UPDATE, DELETE` 即刻失效，AC-AUD-01 必挂。连接串内密码的 `@` 必须编码为 `%40`。

## 3. 文件所有权规则（多人/多子代理协作时强制执行）

> ⚠️ **血泪教训**：本项目在文档编写阶段已实测——**同一文件的多处编辑不能并行**，两次并行写都返回成功，但后写的静默覆盖前写的，且无冲突提示。子代理并行开发会放大这个风险。

**规则：**
1. **一个文件同一时刻只能有一个所有者**。任务派发时必须显式列出 `FILES:`，不同子代理的 `FILES` **不得有交集**。
2. 共享文件（`prisma/schema.prisma`、`locales/zh-CN.ts`、`common/*`、参数表 seed）**默认由主代理独占修改**，子代理需要改动时提交申请，不自行编辑。
3. 子代理完成任务后，主代理必须 `git diff` 复核实际改动范围，确认未越界再合并。
4. 若确需并行：拆成不同模块目录，各自只写自己目录下的文件。

## 4. TDD 适用边界（不是所有代码都要 TDD）

**必须 TDD（先写失败测试，再看它红，再实现）：**

| 领域 | 理由 |
|---|---|
| 奖金池 / 阶梯系数 / 贡献度 / 绩效系数 **全部计算逻辑** | 涉及钱。主 Prompt 给了 4 个算例，验收清单有 AC-INC-12~29d |
| 状态机流转（Gate 双签 3 天弃权、招标、删除审核 2 工作日、移交） | 分支多、易漏出口 |
| 权限守卫与角色隔离 | G-02 硬约束，越权是致命缺陷 |
| 阶段门禁与阻断动作校验 | S/A/B 分级（38/25/14），逻辑复杂 |
| 参数服务取值 | G-08 要求零硬编码 |
| 审计 hash 链 | 断裂即失效 |

**不必 TDD（写完验证能跑即可）：**
Prisma schema 与 migration、seed 数据、DTO 定义、页面布局与样式、i18n 资源、Docker/配置文件、CRUD 脚手架。

> 全量 TDD 会让 P0 工期翻倍而收益极低。**把 TDD 预算压在计算与状态机上。**

## 5. 涉钱红线（P3 阶段专项）

1. 金额一律 `DECIMAL(18,2)`，**禁止 float**。
2. 达成率阶梯为**区间制**，实现方式是"按阈值从高到低，`达成率 >= 阈值` 命中即返回"。
   **禁止 `===` 等值判定，禁止浮点容差**（`bonus.equalityTolerance` 已作废删除）。
   ```
   >120%      → 1.2
   100%–120%  → 1.0   （两端含）
   85%–99.99% → 0.8
   70%–84.99% → 0.6
   50%–69.99% → 0.3
   <50%       → 0
   ```
3. 销售达成口径是**回款**，不是出库、不是开票。取错字段 = 全盘错。
4. 产品与项目是 **1:1**，不做奖金池分摊。
5. P3 完成后必须手工核对 4 个算例：13.2 万 / 24.75 万 / 70% / 120% 端点。**核对不通过不得进入 P4。**

## 6. 状态机速查（完整版见主 Prompt TS-07）

```
项目      DRAFT → TEAMING → ACTIVE →（SUSPENDED）→ ARCHIVED
招标单    OPEN →（SELECTED / EXPIRED / CLOSED）
Gate 评审 PENDING →（APPROVED / REJECTED / ABSTAINED_TIMEOUT）
删除申请  DRAFT → LEADER_REVIEW →（ADMIN_REVIEW → DELETED / REJECTED）
需求      SUBMITTED → ACCEPTED → EVALUATING → SCHEDULED → PROCESSING → CLOSED / ARCHIVED
移交      DRAFT → CONFIRMED → COMPLETED
```

新增任何状态前，先确认它有出口。

## 7. 本项目高频错误（已实际发生过）

| 错误 | 后果 | 规避 |
|---|---|---|
| 并行编辑同一文件 | 静默覆盖，返工 | 见第 3 节 |
| 用建议值冒充制度条款 | 系数算错，奖金发错 | 数值一律回主 Prompt 第 7 节参数表核对 |
| 编号重复（AC-xxx） | 验收追溯失效 | 新增用例前先 grep 现有编号 |
| 硬编码系数 | 制度修订时改代码 | 走参数服务，见 G-08 |
| 给研发PM 阶段加过载设计 | 违背 G-10，系统变味 | 轻管只三字段 |
| 写"100%闭环" | 违反 G-06 | 未知状态显式写"待补充" |

## 8. 提交规范

- 分支：`main` / `feat/P0-base` / `feat/P1-ipd` / `feat/P2-dualpm` / `feat/P3-incentive` / `feat/P4-periphery`
- 提交信息：`feat(P1): <描述>` / `fix(P3): <描述>` / `test(P3): <描述>` / `chore: <描述>`
- **每个阶段结束打 tag**：`v0.1-P0` / `v0.2-P1`… 便于验收不通过时回滚
- 频繁提交：一个测试变绿就提交一次

## 9. 构建顺序（禁止跳阶段）

```
P0 底座 → P1 IPD 主干 → P2 双PM 机制 → P3 绩效与激励 → P4 外围闭环
```

每阶段结束：启动服务 → 跑该阶段验收清单 → **全部通过**才进入下一阶段。
**禁止一次性生成全部代码。**

## 10. 与 Superpowers 工作流配合（如使用 superpowers skill）

> ⚠️ 该 skill 原文面向 OpenClaw（用 `sessions_spawn`），在 WorkBuddy / Claude Code / Cursor 环境下需按本节适配。

**适配映射：**

| Superpowers 原设计 | 本项目适配 |
|---|---|
| `sessions_spawn` 派发子代理 | 用 `Agent` 工具（`subagent_type: general-purpose`）。派发模板见本节末尾 |
| Phase 1 Brainstorm（从零设计） | **跳过**。本项目已完成 33 项决策 + 12 项边界裁定，brainstorm 会推翻已定案内容 |
| Phase 2 Writing Plans | **保留**，但 plan 的 task 粒度按本文件第 4 节的 TDD 边界切分，不要对 CRUD/配置类也套 TDD |
| Phase 3 Subagent 循环 + TDD | **保留**。TDD 只用在第 4 节"必须 TDD"的领域 |
| spec-reviewer 子代理对照 plan | **改为对照 `IPD系统_验收清单.md` 的 AC-xxx 编号**。本项目已有 235 条用例，比对照 plan 精确得多 |
| Phase 5 finishing-branch | 本地项目无 remote 时，只做：全量测试通过 → 打 tag（`v0.1-P0`）→ 询问是否合并到 main |

**关键差异（必须知道）：**
1. **不要 brainstorm**。规格已冻结，brainstorm 的输出一定是回归。
2. **子代理是全新上下文**——不要投喂整份 1307 行主 Prompt（注意力稀释，硬约束会被忽略）。只给：本文件全文 + 主 Prompt 相关章节切片 + 具体 task。
3. **子代理之间的 `FILES` 必须互斥**（见第 3 节）。Superpowers 原生设计没有这条，但本项目实测会静默覆盖。

**派发模板（替换 skill 原文的 sessions_spawn 模板）：**

```
目标（一句话）：
背景：IPD 产品经理管理系统，当前处于 P{0-4} 阶段
必读：① 仓库根目录 CLAUDE.md（即本文件）② 主 Prompt 第 {N} 节 {章节名}
你要改的文件（FILES，与其他子代理互斥）：{精确路径列表}
不要碰：{其他文件路径}
约束：TDD（若属第 4 节"必须 TDD"领域）；YAGNI；不得修改不属于本 task 的文件；
      不得硬编码任何系数/阈值/期限（G-05/G-08）
验收：跑通 `IPD系统_验收清单.md` 中的 AC-{范围}；命令 {测试命令}
任务：{从 plan 文件粘贴的完整 task 文本}
```

## 11. 动手前先确认（防止白干）

1. 你正在做哪个阶段？去主 Prompt 第 8 节读该阶段的构建指令与验证条件。
2. 你要改哪些文件？确认未与他人的 `FILES` 冲突。

4. 涉及数值吗？去第 7 节参数表取，不要凭常识填。
5. 完成了吗？打开验收清单，逐条打勾，未通过的列出来。
