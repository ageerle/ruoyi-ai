## 5 层根因（沿用前端漂移反思模式）

### 1. 缺业务架构师
ZK-IPD Prompt 是前端 React + 后端 Java 双侧共用真理源；本仓 P2-3.x 卡族对 Prompt §三.2 奖金池规则的解读与 Prompt 原文有口径偏移（target vs receipts、coefficient vs tierCoefficient），**说明 owner 给规则但未给推导路径**，缺业务架构师把规则"翻译"成后端可执行的强类型公式。

### 2. 仓物理隔离（Java enum 强类型 vs ZK-IPD React 弱类型）
ZK-IPD 前端用 React 弱类型字段名，奖金池用 `actualReceipts` 与 `targetSales` 两种名并存都能跑；后端 Java 用 BigDecimal 强类型，`coefficient` 字段已建模但服务层零引用——**字段定义 vs 字段使用两层真相**在编译期不会报错。

### 3. 业务规则铁律缺失
owner 只给 G-01~G-11 约束级（顶 7 条硬约束），没下沉到"ZK-IPD Prompt §X.Y.Z = Java Y.y()" 业务域级映射。每个 P 卡按 owner 给的 AC 写测试，但 AC 是从 Prompt 衍生出的子集（只覆盖当前卡相关条款），无法捕获跨条款的整体公式语义。

### 4. 质量门不含业务一致性
98.9% 测试通过率是功能正确性代理，不验证业务规则是否对齐 ZK-IPD。`BonusPoolService` 有 0 个测试文件（`ls test/java/...service/ | grep -i bonus` 空结果），意味着公式变更无回归保护。

### 5. 谁后写谁占主导
P2-3.x 卡族（奖金池相关）的 owner 在 AC-INC-16 注释里直接写了"目标销售额 × 5%"（ZK-IPD 原文是"实际回款金额"）——**是 owner 把 ZK-IPD 误读成了 target**，且后续 SEC/CODE/PERF agent 全员基于这个错误 AC 写测试，错上加错。
