## 2. 深度反思

### 2.1 根因分析（5 簇）

#### 簇 X1：汇总卡 = "假完成" 的最大风险

**症状**：23 张 ⬜ 卡在镜像里写着"原 41 项计划"，但所有卡的责任泳道都写"阶段负责人汇总（不作为执行认领卡）"——**这是治理上明确允许"暂不拆"的口径**，但**在 user 偏好"全部完成后才允许停止"的高压下变成了"等阶段负责人来认领"的真空**。

**根因**：原计划阶段是"理想化"分期，目标是"做哪几段"；但**执行层是"一张张独立可认领卡"**——两者在用户偏好 5★的"不允许形式化"下必须**全部拆解为可独立验收的子卡**。

**对策**：本轮 23 张 ⬜ 卡全部按"5 列补齐"提案（附录 A）；每张卡可由独立会话认领，单测+真库 HTTP+commit+manage.py set 闭环。

#### 簇 X2：单写入者 vs 蜂群并行的硬冲突

**症状**：用户偏好 5★"蜂群并行 + 全部完成后才允许停止"；项目纪律 OPS-09"单写入者 + 串行主链"。

**根因**：用户从"产出端"提要求（全部完成），项目治理从"质量端"约束（避免假红假绿）。**两者在"23 张下游卡，每张真库闭环"场景下不可同时满足**——除非：

- 把"蜂群"重新定义为"**多会话串行认领 + 错峰执行 + 共享 SSOT**"（即"按泳道分布式推进"），不是"同时改同一文件"
- 把"全部完成"重新定义为"**循环推进，按优先级分批，每批真闭环**"，不是"一个 turn 全做完"

**对策**：本轮已与 owner 拍板采用 A 路线（只读盘点+治理+试跑 P2-1）；后续 23 张卡按"批次 1/2/3"串行推进。

#### 簇 X3：working tree 不洁 = 真闭环的"假绿"隐患

**症状**：当前 11 个 unstaged 改动，全部是兄弟会话在 P1-4/5 推进中的活。如果我直接 `mvn -o -pl ruoyi-modules/ruoyi-ipd test`，结果可能 sibling 改完的 245/245 全绿算到本会话头上。

**对策**：本会话所有"测试"只跑**完全自己 own 的最小切片**（如 P2-1 的 ServiceTest），**不跑全模块 mvn test**（避免误判）；只跑 `mvn -o -pl ruoyi-modules/ruoyi-ipd -Dtest=P2XxxAcceptanceTest test` 这种错峰单模块形式。

#### 簇 X4：5 张 ◐ = 接近完成但永远差一步

**症状**：5 张 ◐ 卡（数据模型 / 参数种子 / 响应包络 / 审计链 / 认证状态机）的"骨架有，真库实灌未跑"是一个长期慢性问题——因为：
- Mock 测试 = 8~10 绿 → 看起来"完成"
- 真库 = 多个配置文件 + 多个迁移脚本 + 真 MySQL 启动 + curl HTTP 实跑
- 真库 = 兄弟会话的写权限冲突 → 拖到现在

**对策**：5 张 ◐ 卡优先于 23 张 ⬜ 推进（一周内可全部闭环），每张卡用"真库单测 + 真库 HTTP + 文档"三件套闭环。

#### 簇 X5：前端子卡 + 跨仓库契约 = P4 阶段的盲区

**症状**：P4-1~4 几乎全部依赖前端（49 页 / 报表 / 需求门户），本仓库是后端，前端在 `ruoyi-web` / `ruoyi-admin` 独立仓库；本仓库不能直接闭环。

**对策**：P4-1~4 拆"前端 issue 占位卡（跨仓库）" + "后端契约卡（本仓库）"两个独立子卡；P4-5 验收回归在最后串行。
