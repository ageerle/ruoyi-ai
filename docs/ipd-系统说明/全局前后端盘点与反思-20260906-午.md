## 四、深度反思（结构性，不是单点 bug）

1. **"后端先行"缺消费对账**。190 端点里 22 个零消费，最久的（协作圈）后端按原型逐字交付，前端 Tab 却不存在于任何待办——每张后端卡都验收了，"谁来实现第一个调用者"没有卡。修复不是补页了事，而是把「端点消费对账」变成例行盘点：交付超过一个迭代仍零调用的端点，要么排前端卡、要么显式登记为预留能力。
2. **验收按页过、没人走用户路径**。协同绩效断裂（菜单占位 vs 子页真组件）在今天下午的 KPI/激励落地中刚发生过：改 children 的人不看父级菜单，因为卡片按页拆、完成判据只到"本页真组件"。应收一道「菜单→功能→落库」的走查：每收口一域，点一遍真菜单。
3. **pending 占位是只增不删的**。同名能力一真一假两条路由（本息 P0-10.37、一度 P0-10.32）会误导后续会话把占位页当成"还没做"。pending 必须随真组件落地同步删除或转 redirect，本仓缺这条收尾纪律。
4. **每层各自绿 ≠ 系统绿**。前端 356 用例全部 mock fetch（绿的是"组件按契约渲染"），后端 138 测试类全绿（绿的是"服务按契约行为"），但真 HTTP 一条没跑——接缝靠联测卡，而联测永远排在最后。今天又验证了一次：前端全绿 + 真库 3 超管违例存量，超管移交真链路依然一步都走不通。真库存量治理（卡 288e0d6b）与联测卡应视为 P2-7.3 关卡的一部分，而非"后续优化"。
5. **多会话共工下，盘点结论必须带时间戳**。本次盘点期间 ipd.ts 在 10:08 仍被兄弟会话改写，同分钟内 grep 与 Read 结果不一致。任何"前端还没做"的断言（包括本文件）下结论前都要重对磁盘现态——上一份交接里"页49 完全没做"过时就是同一成因。
