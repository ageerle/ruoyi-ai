## 5 层根因（沿用前端漂移反思模式）

### 1. 缺业务架构师（最关键）
ZK-IPD Prompt 是前端 React + 后端 Java 双侧共用真理源；本仓 P2-3.x 卡族对 Prompt §三.2 奖金池规则的解读与 Prompt 原文有口径偏移（target vs receipts、coefficient vs tierCoefficient），**说明 owner 给规则但未给推导路径**。

**对照证据**：`BonusPoolService` 行 18 注释直接写「AC-INC-16：奖金池基数 = **目标销售额** × 5%」，而 ZK-IPD Prompt §三.2.1 原文是「**实际回款金额** × 5%」。owner 把"销售额"误读为"目标销售额"（不是"实际回款"），且后续 SEC/CODE/PERF agent 全员基于这个错误 AC 写测试，错上加错。

**类比前端漂移**：前端 React 弱类型字段名 + 视觉参考图多源 → 漂移。后端 Java 强类型 BigDecimal + 注释强语义 → 本不该漂移，但**注释也是人写的，注释错了编译器不报**。

### 2. 仓物理隔离（Java enum 强类型 vs ZK-IPD React 弱类型）
ZK-IPD 前端用 React 弱类型字段名，奖金池用 `actualReceipts` 与 `targetSales` 两种名并存都能跑；后端 Java 用 BigDecimal 强类型，`coefficient` 字段已建模但服务层零引用——**字段定义 vs 字段使用两层真相**在编译期不会报错。

**佐证**：
- `BonusPool` 实体行 53-54 有 `coefficient` 字段，注释明确写「项目系数（S/A/B，G1 双签决定）」
- `BonusPoolService` 全文 grep `coefficient` 零结果（除 ZK-IPD 2026-09-06 补的方法）
- 字段定义 ≠ 字段使用 = 孤岛

### 3. 业务规则铁律缺失
owner 只给 G-01~G-11 约束级（顶 7 条硬约束），没下沉到"ZK-IPD Prompt §X.Y.Z = Java Y.y()" 业务域级映射。每个 P 卡按 owner 给的 AC 写测试，但 AC 是从 Prompt 衍生出的子集（只覆盖当前卡相关条款），无法捕获跨条款的整体公式语义。

**佐证**：
- `ProjectService.computeBonusPool(targetSales, coefficient)` 行 142-147 用 targetSales（错误口径），与 ZK-IPD §三.2.1「实际回款」冲突
- `CoefficientChangeService` 维护 project.levelCoefficient 字段（S/A/B 系数），但下游 BonusPoolService 完全不消费
- AC-INC-16 注释行 18 把 targetSales 当默认，**注错源头**

### 4. 质量门不含业务一致性
98.9% 测试通过率是功能正确性代理，不验证业务规则是否对齐 ZK-IPD。`BonusPoolService` 有 0 个测试文件（`ls test/java/...service/ | grep -i bonus` 空结果），意味着公式变更无回归保护。

**佐证**：
- `mvn test -pl ruoyi-ipd` 总测 846，3 failures / 4 errors。但 `BonusPoolZkFormulaTest`（本轮新增）7/7 绿
- P343AcceptanceTest.noFloatEqualityInTierMatching 检查 BonusPoolService.java 源码不含 `===`，是**风格门**而非**业务规则门**

### 5. 谁后写谁占主导（多 agent 并行写测试）
P2-3.x 卡族（奖金池相关）的 owner 在 AC-INC-16 注释里直接写了"目标销售额 × 5%"——**是 owner 把 ZK-IPD 误读成了 target**，且后续 SEC/CODE/PERF agent 全员基于这个错误 AC 写测试，错上加错。

**佐证**：
- BonusPool 实体行 13 注释 = 「目标销售额×5%×系数→6档阶梯」（完全 targetSales 口径）
- BonusPoolService 行 18 注释 = 「AC-INC-16：奖金池基数 = 目标销售额 × 5%」（同 targetSales 口径）
- CoefficientChangeService 行 119-122 写入 project.levelCoefficient（S/A/B 系数），但 BonusPoolService 不消费

**3 个独立写注解的人**（BonusPool 实体、BonusPoolService、CoefficientChangeService）一致走 targetSales 口径 → **群体盲点**，与 ZK-IPD 真相源分歧却无人发现。

## 落地对应（5 项）

1. **新增 BonusPoolZkFormulaTest.java（7 测）**——把 ZK-IPD §三.2.1 公式从「注释 + 文档」下沉到「JUnit 测试断言」，任何后续重构触发公式变更都会被这 7 测拦截。
2. **新增 BonusPoolService.calculateBonusPoolByZkFormula**——ZK-IPD 公式纯函数（无副作用），可单独调用、可单测；与既有 calculateBasePool/FinalPool 并存，不破坏既有 38+ 调用方。
3. **新增 BonusPoolService.buildPoolFromProject**——消除 BonusPool.coefficient 字段孤岛（之前 service 层零引用，project.levelCoefficient 写入后下游不消费）。
4. **保留既有路径**——calculateBasePool/FinalPool/tierCoefficientOf 等保持原样；本轮只新增方法不修改原逻辑，避免引入兼容风险。
5. **不修 P1/P2 项（超预算）**——奖金分配比例算法、超管权限移交专属路径、招标到期提醒等已识别但未 TDD 闭环，留给后续卡片。
