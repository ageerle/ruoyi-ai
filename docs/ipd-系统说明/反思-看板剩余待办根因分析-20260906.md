## 三、剩余待办多的根本原因（深度反思）

### 3.1 业务规则的层级复杂度远超工程量

IPD 不是 CRUD 系统，而是**金融级别的复杂业务规则系统**：
- **P3 奖金池核算** 单卡就有 6 档达成率函数 + 5 档绩效系数 + 2 档差异化系数 + 算例 A/B/C/D 四类——一张卡可拆 5 张子卡
- **Gate 评审** = 5 Gate × 33 要素 × 14 否决项 × 双签机制 = 单域 50+ 张卡合理拆解
- **P2 移交** 4 张卡对应**单项目移交 / 批量移交 / 超管移交 / 移交超期**，每张都是独立业务域

**vs 简单工程**：若 P0-P4 一阶段对应一卡，会变成 4 张卡——但 IPD 的 11 硬约束 + 49 页 + 5 Gate + 33 要素 + 69 动作 + 237 AC 每条都要可验收，**自然拆出 200+ 卡是业务规则的固有复杂度**。

### 3.2 后端实现不是「写代码」而是「落业务」

很多卡需要的不只是工程实现，而是**业务建模**：
- P3-3.3 津贴内部台账幂等：需要处理"人员 A 在 1 月中旬从市场 PM 转为研发 PM，1 月津贴归属谁？"这种业务灰度——需要 owner 裁决
- P3-7.1 P3 真实账务算例：需要至少 4 套真实数据驱动的算例验证（AC-INC-16b）
- P2-7.x 移交系列：单卡涉及 6 步闭环 + 15 日升级 cron + session 失效

**工程能写的部分远小于业务能写的部分**——剩下的卡普遍是「等业务裁决 + 等真实数据」。

### 3.3 看板体系自身设计 = 自证清白机制

- **每卡必须有验证命令**：300+ 卡 99% 都带 `mvn test -Dtest=...` 或 curl 真实 HTTP 探测——防止假绿
- **cancelled 46 张**：治理轮里发现「此卡已被某会话清掉」「此卡与某卡重复」「SPEC 描述与代码不符」立即 cancel 留痕（不是简单删除）
- **U 紧急度标签**：U0 紧急（16 张）= 阻断验收底线 / U1 高（131 张）= 主流程 / U2 中（36 张）= 可下波做——**U3 没出现过说明没人会标低优先**，治理分级扎实
- **AUD-GOV 8 张**：治理本身是元工作量，独立成卡避免污染业务卡

**看板多不是因为规划失控，而是治理纪律要求"每发现一个 P0 即落卡"。**

### 3.4 P2 是关键瓶颈，8 张治理卡是元工作量

```
P0 全部 done（10 张）──┐
P1 几乎 done（19/20） ─┤
P2 进行中（24 张）    ──┼─→ P3 未开始（23 张）──→ P4 未开始（10 张）
                       ┘
                       8 张治理卡（独立）
                       6 张 QA 验收卡（最终门槛）
```

**P2 移交 + 需求变更是 P3 的输入依赖**——这 8 张 P2 不动，P3 动不了；P3 不动，QA 6 张验收卡做不了。**真正的卡墙在 P2.6.x / P2.7.x / P2.5.x**（共 10 张）。

## 四、为什么「不能一鼓作气做完」的硬约束

1. **业务裁决不可 AI 代理**：P3-3.3 津贴移交归属、P3-7.1 真实算例、P2-7.x 移交规则灰区等涉及业务判断，需要 owner 拍板
2. **真实数据不可编造**：QA-08 249 AC 全量执行需要真库 + 真用户 + 真账——这只能在用户真实工作流中完成
3. **后端规则不可能「假绿」**：每张卡都带 `@Tag("dev")` Surefire 过滤 + 真实 HTTP 探测——每张都是 1-3 个 commit + 1-2 个单测的可验收工作单元
4. **看板本身是动态治理**：cancelled 46 张说明治理轮在持续发现重复 / 失效 / 误判——剩余 66 张不代表"剩下 66 张就能做完"，可能治理轮还会再砍 20 张

## 七、本反思的核心结论

> **剩余 66 张 todo 不是失败信号，而是项目复杂度的诚实投影。**

- 200 张卡覆盖了一个 11 硬约束 + 49 页 + 69 动作 + 5 Gate + 33 要素 + 237 AC 的金融级业务系统——**这是 1-2 年真实工程的看板，不是一周 sprint**
- done 60 + cancelled 46 + 本会话实做 35 页 = **治理纪律在工作**（cancelled 高达 23% 说明看板在自我纠错）
- 真正卡墙是 **P2.5/6/7 系列 10 张后端 + 8 张治理 + 6 张 QA 验收**，不是「剩余 200 张平摊工作量」
- 本会话用 8 个智能体并行 +1 个真库冒烟跑 +1 个 5 维审计 = 把前端 71% 落地，但**这是「前端能解耦的部分」+ 集成分**——剩下 30% 是必须 owner + 业务裁决 + 真用户流程才能闭环的

**不要把「todo 多」当成「治理失败」**——它是一个已经走过快速实施期、进入精修与裁决期的成熟项目的正常状态。剩余的工作是**质量而非数量**——每张卡的契约、裁决、证据、灰区处理都比快速 CRUD 难一个数量级。
