## 5. A′ 链在 100 并发 HTTP 写下的自洽铁证（QA-05-P2 闭环证据）

- 冒烟：锚播 `next_seq=503432` → 首登录写入 `seq=503432`，`prev_hash` 精确等于 503431 行 `curr_hash`（`2ee50f63…`）
- 压测全量（含 100 并发 3 场景 + 16 并发对照）：新增审计 **3,948 行（seq 503432..507379），`LAG()` 验链 0 断裂**，锚 `last_seq(507379) ≡ max(seq)(507379)`
- 结论：A′ 悲观锁串行化在真实 100 并发 HTTP 下零断链、零跳号——QA-05-P2「HTTP 闭环验收复跑」残留项就此补齐。

## 6. 归因（四路证据）

1. **池监控**（/tmp/qa05p1-final-16046.log）：`SQLTransientConnectionException … timed out after 5001ms (total=40, active=40, idle=0, waiting=39~78)` 共 **1,121 次**——池 40 满载。但失败为 5s 快速失败（修复目标行为），非 30s 雪崩。
2. **DB 无罪**：mysqld CPU 0.1%；d 场景 88 TPS 下零错误。
3. **slow log（本波已开 0.5s 阈值，第二波 QA-05-P3 交付项）双证据**：
   - `SELECT COUNT(*) FROM audit_logs` 反复 0.52–0.65s——OFFSET 分页的 count 代价，正是 QA-05-P3 游标模式（`searchCount=false`）所规避的对象；d 场景 DB 侧延迟贡献即此，游标端点推广后可消；
   - 锚行 `SELECT … FOR UPDATE` Lock_time≈Query_time≈0.5s 少量出现——100 并发写串行排队的预期表现（锁内执行极快，纯等待），16 并发时消失。
4. **CPU 容量才是剩余瓶颈**：登录 = BCrypt(cost 10) ~100ms CPU/次；可用核 ≈10−3（邻居）→ 理论登录 TPS 上限 ≈70（实测 60.7 吻合）。100 并发下 p50 排队 ≈100/70×每请求成本 → 秒级；叠加池 40 边界 → 5s 快速失败吸收超额部分。

## 7. P4（BCrypt 容量预算）评估（不写代码，并入本报告）

- **现状**：cost=10，单次校验 ~100ms 纯 CPU；10 核满额理论登录 TPS ≈ 100，共享环境（3 核被占）≈ 70。
- **判定线推演**：`写 P95<3s` 在独占 10 核 + 100 并发下可达（p50 排队 ≈1.4s）；本机蜂群共享环境不可达——**判定线未达是容量/环境问题，不是配置缺陷**。
- **建议**：维持 cost=10（降 cost 削弱口令安全，不值）；登录高峰走扩容（水平实例）或限流排队；`application.yml` 基座 maxPoolSize=20 注释中的连接预算公式（实例数×池≤151）继续有效。
- **后续**：登录容量专项若要 100 并发 P95<3s 达标，需独占机器复测一轮（判定线本意），归 QA-05 泳道运维侧。
