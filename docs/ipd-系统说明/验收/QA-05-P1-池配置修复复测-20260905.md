### 4.2 剩余瓶颈 = 审计 hash 链写串行化（**属 QA-05-P2，本卡不修**）

- **现象**：池=40、connectionTimeout=5s 下，100 并发下 a/e 仍大量 `SQLTransientConnectionException`，错误样态 100% 为「连接超时前未拿到」。
- **拐点证据**：错误发生时 `active=40, idle=0, waiting=95` ——所有 40 个连接都被占满且不释放。说明事务平均持池时间 > 50ms（100 请求 × 50ms / 40 连接 = 满载），实际远大于此。
- **根因链（沿用 QA-05 §5.3）**：登录链路 = BCrypt(cost 10) + sa-token 会话 + persons.last_login_at UPDATE + 审计 INSERT；transit 链路 = 乐观锁 UPDATE + **审计 hash 链 `ORDER BY seq DESC LIMIT 1` + INSERT**。每条写事务都在 50 万行 audit_logs 上做倒序读 + 写，串行化使单事务持池时长远超 BCrypt/乐观锁本身的 CPU 耗时。
- **不属于本卡的修复点**：池容量已不是瓶颈（再上调到 100、200，错误率不会线性下降；a/e 链路即使池无界，单次事务的串行化仍限制 TPS）。QA-05-P2 应聚焦 `audit_log_chain_heads`（泳道锚表）/ 缓存 prev_hash / 事务外计算哈希。

### 4.3 列表 b 临界超标分析

b 现 p95=1495 / p95_max=1563；基线 1338。差值集中在 p95 段（p50 847 vs 759、p99 1699 vs 1506），呈全段上移。原因：

- 蜂群并发环境的本机共享压力（QA-05 §1「load average ≈6.4/10 核」声明的本机共享开发环境噪声）
- b 场景是「超管全量 2000 行不分页」——数据规模未变（同样 2000 projects），但兄弟流对 audit_logs 的写入活动增加了 ibd 文件膨胀与 InnoDB B+ 树碎片，扫描路径上的 latch 抖动放大
- **不是池瓶颈**：b 错误率 0/1500，所有连接都健康归还

属于蜂群并发基线的可接受噪声，**非本卡回归**；下版基线归一化环境后复测应回归到 < 1338ms 量级。

### 4.4 d 场景（审计分页）改善但仍超判定线

基线 d P95=1640ms，现 1567ms，改善 73ms。但仍超 1500ms 判定线 4%。非池瓶颈（错误率 0），与 b 同源（50 万行表 seq 倒序扫描 + 蜂群噪声）。QA-05 §7 P3 已建议「(seq, 常用列) 覆盖索引 / 游标分页」。
