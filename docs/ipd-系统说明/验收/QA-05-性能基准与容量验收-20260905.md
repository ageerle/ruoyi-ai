## 3. 压测设计与执行

- 工具：Python 3 标准库（`concurrent.futures.ThreadPoolExecutor` + `urllib`），无第三方依赖。
- 模型：固定 100 并发线程池，每场景 3 轮 × 500 请求，轮间 sleep 2s；分位数 p50/p90/p95/p99/max、TPS、错误数。
- 场景：
  - a. 登录 POST /api/v1/auth/login（随机 500 人端到端；另有 50 token 预热）
  - b. GET /api/v1/projects（超管，全量 2000 行，无分页）
  - c. GET /api/v1/stage-actions?projectId=（随机项目，69 行）
  - d. GET /api/v1/audit-logs?pageNo=N&pageSize=200（超管，50 万表 orderByDesc(seq)）
  - e. 写 POST /api/v1/stage-actions/{id}/transit?target=IN_PROGRESS（MARKET_PM 账号写 MARKET_PM/BOTH 动作；失败回读确认状态）
- 判定线：列表 P95 < 1.5s；写 P95 < 3s。

## 5. 根因分析

**结论：a/e 的失败不是单请求慢，而是并发容量不足导致的连接池雪崩；单请求写路径性能本身优秀（p50≈29ms）。**

证据链：

1. 16040 日志（/tmp/ipd-perf-16040.log）：大量
   `SQLTransientConnectionException: master - Connection is not available, request timed out after 30005ms (total=10, active=10, idle=0, waiting=9)`
   —— Hikari 池 10 连接全占用，100 并发排队 30s 后超时。
2. 超时数值 30005ms 与 Hikari `connectionTimeout` 默认 30s 精确吻合；`ipd-local` profile 无池配置，走默认 maximumPoolSize=10。
3. 写事务持连接时间长放大瓶颈：
   - 登录链路 = BCrypt(cost 10) 校验 + sa-token 会话写 + persons.last_login_at UPDATE + 审计 INSERT；
   - transit 链路 = 事务内乐观锁 UPDATE + **审计 hash 链（SELECT prev_hash ORDER BY seq DESC + INSERT）**——audit_logs 上的排序读使并发写审计事务相互锁等待，事务串行化，池占用时间倍增。
4. 对照实验：并发降到 8（<池 10）后 a/e 全部达标且吞吐健康（写 TPS 240、P95 67ms），排除 CPU/DB 资源饥饿（压测时 mysqld CPU≈1%，load 来自邻居 agent 而非被测链路）。

## 6. 慢查询观察

- MySQL `slow_query_log=OFF`、`long_query_time=10s`（.codex 本地实例默认），未能取到慢查询明细；全局 `Slow_queries` 计数器=7（含邻居活动，无归因价值）。替代证据：Hikari 等待日志（§5.1）+ `SHOW VARIABLES` 抽样。
- 建议：ipd-dev 本地实例开启 slow log（`long_query_time=0.5s`）后复测一轮，聚焦 audit_logs 的 seq 倒序分页与 hash 链 prev 查询。

## 7. 问题清单

| # | 级别 | 问题 | 建议 |
|---|---|---|---|
| P1 | U0 | **登录/transit 写路径在并发>10 时雪崩**（池 10 + 30s 超时），100 并发下错误率 ~100% | ipd-local/dev profile 显式配置 hikari（建议 maxPoolSize≥40、connectionTimeout≤5s 快速失败）；生产 20 亦不足 100 并发，需同步上调 |
| P2 | U1 | **审计 hash 链写入使写事务串行化**（transit/login 均写审计，50 万行表上 ORDER BY seq DESC 取 prev_hash），是写事务持池时间长的主因 | hash 链头改缓存/专用锚表（audit_log_chain_heads 已存在可复用），或 prev_hash 计算移出事务 |
| P3 | U1 | audit-logs 分页（50 万表、pageSize=200、seq 倒序）P95≈1.64s，稳定超出 1.5s 判定线约 9% | 覆盖索引 (seq, 常用列) 或游标分页（WHERE seq < lastSeq LIMIT 200） |
| P4 | U2 | 登录 BCrypt cost 10 单次 ~100ms CPU（本报告造数无法改证书成本，属安全参数权衡），高并发登录叠加上限放大池压力 | 评估 cost 8-10 与登录 QPS 容量的安全预算 |
| P5 | info | 本地 .codex 实例 slow log 未开启，慢查询不可观测 | dev 实例开 slow_query_log 供后续 QA 复用 |

## 8. 判定结论（逐项）

| 验收项 | 要求 | 实测 | 结论 |
|---|---|---|---|
| 隔离数据规模 | 500 人/2000 项目/50 万审计 | 500/2000/500000（另 138000 stage_actions、12000 stages） | ✅ |
| 100 并发 | 100 并发线程池 | 100 并发 × 3 轮 × 500 请求 × 5 场景 | ✅ 执行完成 |
| 列表 P95 | <1.5s | b=1338ms ✅；c=1233ms ✅；d=1640ms ❌ | **部分达标**（2/3，d 临界超标 9%） |
| 写 P95 | <3s | 100 并发=30378ms ❌；8 并发=67ms ✅ | **不达标**（容量拐点 10~20 并发，单请求性能达标） |

**总体：QA-05 容量验收不通过（有条件）。** 首版基线结论：系统在 ≤10 并发下全部场景达标且性能优异；当前配置无法承载目标容量 100 并发，瓶颈为连接池配置（P1）与审计链写串行化（P2），两项均为配置/结构级修复，不阻塞功能验收，建议开卡跟进后复测收敛。
