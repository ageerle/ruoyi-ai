### 3.2 审计 hash 链完整 —— PASS（连接性口径；重算深度见下）

按 `AuditLogService.verifyChain` / `AuditHashChain`（RISK-04 canonical）规则在 ipd_restore 上全链重算：

- **B1 连接性**（prev_hash==上行 curr_hash、链首 prev=64×'0'、seq 顺序）：恢复侧 353 行断点 **2 处**，与主库基线断点**集合全等** → 恢复未扰动链。断点为主库既有形态：
  - seq=2 seq_gap：audit_logs 无 seq=1 行（链首 prev_hash=GENESIS 正确，种子数据首行即 seq=2）；
  - seq=150 prev_mismatch：并发 append 竞态特征（`selectLast` 与 insert 非原子，两个并发写读同一 last 导致链分叉）。
- **B2 v1 canonical 全量重算**（尽力复现口径）：**261/353 行 curr_hash 完整重算命中**。miss 203 行全部归因：
  - 62 行 `hash_version=2`（canonical-json-v2 历史算法；当前源码 rg 无任何 v2 写入点，属历史版本遗留，无法按现行规则复现）；
  - 1 行 seq=150 断链行（重算输入失真，与 B1 一致）；
  - 其余 140 行：create_time 为 `datetime(0)`，写入毫秒落库即失（含四舍五入进位），脚本按 +08:00 时区 ±1.5s 毫秒容差扫描后，**无 JSON 行 261/284 命中**；有 JSON 行因 MySQL JSON 列规范化（对象键重排）读回文本 ≠ 写入文本，双重不可逆。
  - **活体佐证**：主库基线重算 291/384 命中——比恢复侧多命中的 30 行正是备份后主库新增行（当前代码 append 写入），说明**现行写链算法与本脚本校验口径互相印证**。
- **B3 两侧行级全等**（恢复未扰动链的直接证据）：按 seq 对齐，恢复库 353 行的 `(prev_hash, curr_hash)` 与主库重叠行 **0 差异**，`only_in_restore=[]`（恢复库不含主库没有的行），PASS。

**发现项（不阻塞本卡，建议开卡跟进）**：
1. `AuditLogService.verifyChain` 的「毫秒 + seq 严格连续」语义在 datetime(0) 存储与 auto_increment 跳号现实下会对大量真实行误报断裂——验链可信度弱化，属代码级缺陷（P0-5/RISK-04 遗留）。
2. `hash_version=2` 的 62 行历史数据无对应现行算法实现，链上存在「验不了的行」。
