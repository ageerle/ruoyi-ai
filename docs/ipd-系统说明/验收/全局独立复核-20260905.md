## 三、发现的真实缺陷（认证输入异常 → 统一包络缺口）

**症状**：`IpdAuthServiceTest.changePassword`（L127）与 `.changePasswordMinLength`（L139）断言失败：
```
Expecting actual throwable to be an instance of:
  org.ruoyi.common.core.exception.ServiceException
but was:
  org.ruoyi.ipd.service.IpdAuthInputException: 原密码错误 / 新密码长度至少 8 位…
  at org.ruoyi.ipd.service.IpdAuthService.changePassword(IpdAuthService.java:112 / :108)
```
**根因**：
- `IpdAuthInputException extends RuntimeException`（**非** `ServiceException`）；`IpdServiceExceptionAdvice` 仅有 `IpdBusinessException / ServiceException / MethodArgumentNotValid / NoHandlerFound / Exception` 五类 `@ExceptionHandler`，**无 `IpdAuthInputException` 专用处理**。
- 后果：已认证用户的可纠正输入错误（改密类）落到通用 `Exception` 兜底 → 可能被映射成 **500 泛化包络**而非业务 4xx/`3xxxx`，与 API-01「统一失败包络与错误码」契约、P0-7.2/P0-7.3 认证卡不一致。测试仍按旧契约期望 `ServiceException`。
**性质判定**：属**认证链在途 + 涉设计裁决**的改动（`IpdRolePermissionCatalog.java` 复核时仍 ` M`，兄弟会话刚合入"方案A保留权限码粒度（用户决策）"）。**不由本复核会话抢改**（会复现 §六所述漂移/锁死，且包络映射方向应由 owner 决策）。

**候选修复（交 owner 泳道择一并补测）**：
1. `IpdAuthInputException extends ServiceException`（最小、最快恢复旧契约；确认其消息仍只来自固定枚举、不外泄凭据）；或
2. 在 `IpdServiceExceptionAdvice` 增 `@ExceptionHandler(IpdAuthInputException.class)`，映射到既定业务码 + 4xx（推荐：粒度更清晰，契合方案A）；或
3. 更新 `IpdAuthServiceTest` 断言到新类型 + 对应 HTTP 反例（若新类型即为契约）。
验收：`mvn -pl ruoyi-modules/ruoyi-ipd -am -Dtest=IpdAuthServiceTest test` → 10/0/0，并对改密入口补一条真实 HTTP 反例证明包络状态码与错误码。

3. **[U1·前沿收口] inreview 6 卡**（SEC-02 / API-02 / P0-7.2 / P1-3.1 / P1-5.1 / P1-8.1 等，随动）多为"KEEP_PARTIAL / 需真实 HTTP+DB"。环境（16039+13306）已就绪，可在错峰窗口逐卡跑 `@Tag dev` 验收 + HTTP/DB 正反对齐后收口；涉钱与权限卡不得凭 Mock 关闭。
4. **[结构] 单写协调器纪律**：SSOT/看板/`log.md` 由主协调器串行维护；`manage.py` 写前重算 PLAN 哈希并中途变更即中止——这是护栏，触发中止时**重试或让路**，勿绕过。

## 五、关键风险

- **并发写风险（最高）**：多智能体同时改 SSOT/看板/同一 Java 文件会触发"未纳管卡"拒绝与漂移（本次亲历 SEC-API-02 瞬时锁死后自愈）。
- **假绿/假红双向风险**：假绿 = 无 `@Tag dev` 的测试被 Surefire `<groups>` 静默跳过；假红 = 并发构建污染 `target/`（本次实证）。验收证据须来自"错峰 + XML tests>0 + 真实 HTTP/DB"。
- **雷区（沿用 AGENTS.md）**：`demo.enabled=true` 拦写、多租户 `tenant.excludes`、Langchain4j 三 BOM + gRPC 1.62.2 对齐、git 危险命令被 hook 拦截（`push`/`reset --hard` 等需用户授权）。
- **提交积压**：`main` 领先 `origin/main` 数十提交未推送（hook 拦截，需明确授权）。属发布决策，不在本复核处置范围。

## 六、看板处置说明（为何本轮不强行写板）

复核时看板处于 `has_drift: True / 未纳管卡 1` 的**活跃对账中**（兄弟协调器正把 inreview→done、纳管/回收卡）。`manage.py set` 结尾会 `reconcile(apply=True)`，此刻执行会撞上未纳管卡守卫而**中止**（与亲眼所见的 SEC-API-02 锁死同源），反而由本会话引入新漂移。**单写协调器 SSOT 下，第二方强行写板是制造漂移的反模式。** 故本轮以本报告作为不冲突的验收证据物（对齐 `验收/*-QA独立复核-*.md` 约定，即前沿卡 evidence 指向处），待看板 `check` 归零漂移后，再由协调器/本会话追加一次性 `set` 登记引用本报告。此为对 §四-4 纪律的遵守，非"只给建议"：真实构建/测试已执行、缺陷已定位并给到可复现证据与候选修复。

**实证补充（复核末）**：连续 12s 三次 `check` 均为 `has_drift:True / 未纳管卡:1`，唯一未纳管卡即 `[AUD-GOV-01] [U0] 全局闭环治理盘点与蜂群执行`——**兄弟会话已为本类"全局治理+蜂群执行"任务在看板建卡（board-only，待回写 SSOT）**。若本会话再建 SSOT 行或写板，将与之直接竞争同一协调卡。故本报告的定位是：作为 AUD-GOV-01 之外的**独立第二方复核证据**，交协调器归并，而非重复建卡。
