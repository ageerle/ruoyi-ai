## 2. ⚠️ P1-1（**U0，量化风险，原报告未覆盖**）：基线块使 ipd-local 池 4× 放大，4 实例并存即超 MySQL 连接上限

### 2.1 事实

`application.yml` 新增的基座块 `spring.datasource.dynamic.hikari.maxPoolSize: 40` 的**设计意图**是给「未显式配池的 profile（如 ipd-local）提供安全基线」（原文注释）。但 ipd-local 正是本仓**所有实测实例使用的 profile**（实证：`.codex/ipd-dev/runtime/ruoyi-admin-def6i.log` 中 `The following 1 profile is active: "ipd-local"`），因此该基线把 ipd-local 的池容量从 **HikariCP 默认 10 直接提到 40，放大 4 倍**。

### 2.2 实测连接预算（2026-09-06 10:19 CST 取证）

```
SHOW VARIABLES LIKE 'max_connections'          → 151
SHOW GLOBAL STATUS LIKE 'Max_used_connections'  → 81      （历史峰值，54% 水位）
SHOW GLOBAL STATUS LIKE 'Threads_connected'     → 41
SELECT user, COUNT(*) FROM information_schema.processlist GROUP BY user
    → ipd_app 40 | root 1 | event_scheduler 1
SELECT db, command, COUNT(*) ... WHERE user='ipd_app' GROUP BY db, command
    → ipd_dev | Sleep | 40
```

在跑实例数（`lsof -nP -iTCP -sTCP:LISTEN | grep java`）：**4 个** —— 16039(PID 76237)、16044(p041.jar)、16045(def6i.jar)、16050。

### 2.3 量化闭合（这是本项的核心证据）

当前 4 个实例**全部是不含 d9c24227 的旧 jar**，ipd-local 无 hikari 块 → 各自使用 HikariCP 默认 `maximumPoolSize=10`：

```
4 实例 × 10 = 40  ≡  实测 ipd_app 连接数 40（且 100% 为 Sleep 空闲保活）
```

**精确吻合**，且「全 Sleep」证明连接数由**池预留**决定、与业务负载无关（零负载也常驻）。由此可外推换成新 jar 后：

| 场景 | 池/实例 | 实例数 | 峰值连接需求 | vs max_connections=151 |
|---|---|---|---|---|
| 现态（旧 jar，默认 10） | 10 | 4 | 40 | ✅ 27% 水位（实测已验证） |
| 新 jar，2 实例 | 40 | 2 | 80 | ✅ 53% |
| **新 jar，4 实例（本仓常态）** | **40** | **4** | **160** | ❌ **超 9 个 → `ERROR 1040 Too many connections`** |
| 新 jar，4 实例 + 1 压测实例（复测常态） | 40 | 5 | 200 | ❌ 超 49 个 |

`Too many connections` 是**比池排队雪崩更严重的硬失败**：新实例根本起不来、运行中实例无法获取连接、且 ipd_app 非 SUPER 用户拿不到 MySQL 为管理员保留的额外连接（仅 root 运维通道可用）。

### 2.4 与原报告的关系

原报告 §6 建议 3 已提到该耦合（「40 实例池 × N 实例需 ≤ 151」）但列为 **U2** 且**未量化当前 N**；本复核实测 N=4 且已验证 4×10=40 的对应关系，故 4×40=160 超限是**确定性结论而非推测**，级别应为 **U0**（阻塞「把新 jar 推到全部实例」这一必然动作）。

### 2.5 建议（三选一，均不需回滚雪崩修复）

1. **推荐**：基座块 `maxPoolSize` 取 **20**（与 prod 现值一致）→ 4×20=80，53% 水位，留 71 个连接给压测/运维实例；dev 若要 40 则保留 dev 独有覆盖，基座只作兜底。
2. 或先把 MySQL `max_connections` 提到 ≥ 250（需评估本机内存：每连接约 ~1–4MB 缓冲），再上 40。
3. 或在 `application-ipd-local.yml` 显式配 `maxPoolSize: 20`，使基座 40 只对未来未知 profile 兜底（同时顺带修 §4 的配置漂移）。

## 3. ⚠️ P1-2（**U1，结论级假绿**）：§5.2.3「DB 直查为权威依据」不成立

### 3.1 原报告结论

§5.2.3：「ipd_dev.audit_logs seq 范围 2..609（起始锚行 prev=GENESIS），**DB 层 prev→curr 衔接校验 100% OK**；DEF-4 `verifyChain` 端点因主实例 16039 jar（早于 DEF-4 提交 7cae2138 之前的构建）无此路由无法直接调用，**DB 直查为权威依据**。」

### 3.2 为什么不成立：verifyChain 有**三条**判据，DB 层 LAG 校验只覆盖两条

`AuditLogService.verifyChain()`（ruoyi-modules/ruoyi-ipd/.../service/AuditLogService.java）的断裂判定是三个条件的**或**：

```java
if (!expectHash.equals(log.getCurrHash())          // ① curr_hash 重算相符
    || !expectPrev.equals(nvl(log.getPrevHash()))   // ② prev_hash 链接相符
    || !expectSeq.equals(log.getSeq())) {           // ③ seq 严格连续 ← DB 层 LAG 校验无法覆盖
    broken.add(log.getSeq());
}
expectPrev = log.getCurrHash();
expectSeq = log.getSeq() + 1;
```

DB 层 `LAG(seq) OVER (ORDER BY seq)` 的 prev→curr 衔接校验只等价于 ①②，**漏掉 ③**。

### 3.3 实测反证（同一份数据、两种判据、结论相反）

| 判据 | 命令 | 结果 |
|---|---|---|
| DB 层链接（原报告口径） | `SELECT COUNT(*) FROM (SELECT seq, LAG(seq) OVER (ORDER BY seq) p FROM audit_logs) t WHERE p IS NOT NULL AND seq<>p+1` | 现态 `gaps=1` |
| DB 层现状 | `SELECT COUNT(*), MIN(seq), MAX(seq) FROM audit_logs` | `626 / 2 / 1326` |
| **应用契约（AC-AUD-03 口径）** | `GET /api/v1/audit-logs/verify`（16045，def6i.jar） | 本会话 P0-9.1 七跑实测 **`chain=BROKEN, broken=[1309]`** |

即：原报告重整后自认「链 100% OK」，而应用端点在同一数据上判定 **BROKEN**。原因是重整只压实了 2..609，而 InnoDB 自增计数器不回填，后续写入落在 1309..1326，形成 609→1309 的**空洞**；空洞后首行 1309 触发判据 ③。

### 3.4 附带更正：应用侧结论**可以**取证，不必以 DB 直查替代

原报告称「主实例 16039 jar 无 verify 路由」。本会话实证 **16045（def6i.jar）该路由可用并已多次成功调用**（P0-9.1 run4–run7 共 4 轮、每轮 4 个检查点均取到 `chain`/`broken`）。故「无法调用 → 以 DB 直查为权威」的前提不成立；正确做法是任选一个含 DEF-4 提交的实例取证。

### 3.5 连带影响

`rebuildChain()` 只重算 `prev_hash`/`curr_hash` 两列、**治不了缺行**，故空洞一旦出现该链**永久 BROKEN 且无法自愈**。此机制连同「`insertStrategy=NEVER` 使 uk_audit_seq 永不冲突 → DEF-4 第 3 修复的冲突自愈重试是死代码」已立案为 **DEF-9**（镜像 L327，U1，deps `P0-5.4,DEF-4,DEF-6`）。

> **本次复核对 DEF-9 定性的一次自我纠错（保留以示范取证纪律）**：初次查 `information_schema.tables.AUTO_INCREMENT` 得 `next_auto=3`，而 `maxseq=1326`，一度推断「计数器落后 → uk 会真冲突 → DEF-4 重试不是死代码」，与 DEF-9 定性矛盾。追加 `SET SESSION information_schema_stats_expiry=0` 后查得 **1327**，`SHOW CREATE TABLE audit_logs` 亦为 `AUTO_INCREMENT=1327`（= maxseq+1，计数器健康）→ **原 `3` 是 24h 统计缓存的陈旧值（偏差 442 倍）**，DEF-9 定性**保持不变**。教训见 §4.2。

## 4. ⚠️ P1-3（U1，权衡未披露）与 info 级发现

### 4.1 `connectionTimeout: 30000 → 5000` 是「P95 换成功率」的取舍，原报告未点明因果

5s 快速失败把「排队 30s 后成功」变成「5s 立即 500」。在 QA-05-P2（长事务持池）未修前，该设置会**把性能瓶颈转化为可见的功能故障**：

| 指标 | 基线（30s） | 现（5s） | 方向 |
|---|---|---|---|
| a 登录错误 | 1500/1500 = **100%** | 935/1500 = **62%** | ✅ 绝对改善 38pp |
| e transit 错误 | 473/500 = 95% | 632/1500 = 42% | ✅ 改善 |
| a P95 | 30046ms | 8978ms | ✅ 改善 70% |
| 错误样态 | 30s 等池超时 | 100%「连接超时前未拿到，事务从未开始」 | — |

需披露的因果：若保持 30s，一部分请求会「慢但成功」，**错误率会更低而 P95 更高**；改为 5s 后 P95 好看但 62% 用户看到 500。这不是要求回滚（5s 快失败对避免线程堆积是对的），而是要求在卡面/报告显式记录该取舍，避免 P2 修复后把「5s」当成既定正确值而不再评估。建议 P2 修复后以「P95<3s **且** 错误率=0」双门复测，再定 connectionTimeout 终值。

### 4.2 info：`information_schema.tables.AUTO_INCREMENT` 有 24h 缓存陷阱（影响所有验收脚本）

`information_schema_stats_expiry` 默认 86400s，导致该列返回严重陈旧值（本会话实测 `3` vs 真值 `1327`）。**任何人/脚本用它判断「自增计数器是否落后于 max(seq)」都会得到相反结论**。建议：验收脚本一律用 `SHOW CREATE TABLE` 或先 `SET SESSION information_schema_stats_expiry=0`。本项已作为可复用 pitfall 沉淀。

### 4.3 info：配置漂移确证（原报告 §6 建议 4 自陈，本会话独立核实）

`.codex/ipd-dev/config/application-ipd-local.yml:14` 的 `master.url` 确指向 `jdbc:mysql://127.0.0.1:13306/ipd_dev`（**非 ipd_perf**），而任务卡描述为隔离库 ipd_perf → 这是 §5.1 事故（1500 次失败登录中 699 行 `perf_*` LOGIN_FAIL 误写主库 `ipd_dev.audit_logs`，seq 区间 549..1264）的**直接根因**。每次用 CLI 覆盖 url 是绕过而非修复；建议直接改配置文件指向 ipd_perf（或在文件内注释显式声明「本文件指向主库，压测必须 CLI 覆盖」）。

# §1.1 生效路径（按缩进还原，非仅 grep）
for f in application-prod.yml application-dev.yml application.yml; do
  echo "== $f"; sed -n '38,90p' ruoyi-admin/src/main/resources/$f | grep -nE "datasource|dynamic|hikari|maxPoolSize|connectionTimeout"
done
grep -n "hikari\|maxPoolSize\|connectionTimeout" .codex/ipd-dev/config/application-ipd-local.yml   # 期望零命中

# §2.2 连接预算
$M --defaults-file=$C -N -e "SHOW VARIABLES LIKE 'max_connections'; \
  SHOW GLOBAL STATUS LIKE 'Max_used_connections'; SHOW GLOBAL STATUS LIKE 'Threads_connected';"
$M --defaults-file=$C -N -e "SELECT user, COUNT(*) FROM information_schema.processlist GROUP BY user;"
$M --defaults-file=$C -N -e "SELECT db, command, COUNT(*) FROM information_schema.processlist \
  WHERE user='ipd_app' GROUP BY db, command;"
lsof -nP -iTCP -sTCP:LISTEN | grep java          # 实例数 N

# §2.3 profile 实证（决定 ipd-local 是否继承基座块）
grep -m2 "profile is active\|profiles are active" .codex/ipd-dev/runtime/ruoyi-admin-def6i.log

# §3.3 / §4.2 链现状 + 自增计数器真值（务必关缓存）
$M --defaults-file=$A -N ipd_dev -e "SELECT COUNT(*), MIN(seq), MAX(seq), \
  (SELECT COUNT(*) FROM (SELECT seq, LAG(seq) OVER (ORDER BY seq) p FROM audit_logs) t \
   WHERE p IS NOT NULL AND seq<>p+1) AS gaps FROM audit_logs;"
$M --defaults-file=$A -N ipd_dev -e "SET SESSION information_schema_stats_expiry=0; \
  SELECT AUTO_INCREMENT FROM information_schema.tables \
  WHERE table_schema='ipd_dev' AND table_name='audit_logs';"
$M --defaults-file=$A -N ipd_dev -e "SHOW CREATE TABLE audit_logs\G" | grep -iE "seq|AUTO_INCREMENT|uk_audit"
