### 11.4 DEF-8 → **已修复并提交 `436262b0`**：归档区恒空（SQL 三值逻辑）

- **现象**：二跑「归档区列表可见该申请」FAIL。真库有 2 行 `status=DELETED` 且 `remark IS NULL`，但 `listArchive()` 返回空。
- **根因**：SQL 是**三值逻辑**——`NULL NOT LIKE '%x%'` 求值为 **NULL（非 TRUE）**，WHERE 不成立 → 行被整条排除。而 `remark` 默认 NULL（submit 与终审均不写 remark）→ **归档区恒空**，AC-DEL-02「数据移入归档区」可见性完全失效，purge 入口也永远拿不到候选。
- **真库对照**：`SUM(remark NOT LIKE '%PURGED%')=NULL`（0 行通过）vs `SUM(remark IS NULL OR remark NOT LIKE '%PURGED%')=2`。
- **修复**：`DeletionArchiveService.listArchive()` 改 NULL 安全 → `.and(w -> w.isNull(remark).or().notLike(remark, PURGED_MARK))`，生成 `(remark IS NULL OR remark NOT LIKE ?)`。

### 12.4 新立案 **DEF-9**（U1，镜像 L327，deps `P0-5.4,DEF-4,DEF-6`，未自行修复）

DEF-6 落地后重跑 P0-9.1 的副产物，暴露一处**比 DEF-6 更深的结构性设计缺陷**——同一处设计的两条耦合后果：

**后果一（并发必断裂 + DEF-4 第 3 修复是死代码）**：`AuditLog.seq` 标注 `@TableField(value="seq", insertStrategy = FieldStrategy.NEVER)` + DDL `seq bigint NOT NULL AUTO_INCREMENT` + `UNIQUE KEY uk_audit_seq(seq)` → 应用**从不写 seq**，入库值全由 DB 赋值。于是 `append` 重试循环内按 `last.seq+1` 自算的 seq **从不入库**，而该自算值却被喂进 `canonicalOf(draft, seq)` 参与 `curr_hash`：

```
并发写者全部读到同一条 last 行
  → 算出相同 prev_hash 与相同 canonical seq
  → DB 却给它们分配互不相同的连续 seq
  → 仅第一条自洽，其余 prev_hash 链接错、curr_hash 内嵌 seq 与实际 seq 不符，且下游全部连带断裂
同时：应用从不写 seq → uk_audit_seq 永不冲突 → catch (DuplicateKeyException) 永不触发
  → DEF-4 第 3 修复「多实例共库靠 uk 冲突自愈重试」是**结构性死代码**
```

**后果二（空洞永久 BROKEN 且无法自愈）**：`verifyChain` 第三条判据要求 seq 严格连续，而 InnoDB 自增值在 DELETE 与事务回滚后**均不回填** → 任何删行或失败 INSERT 都留下永久空洞；`rebuildChain` 只重算 `prev_hash`/`curr_hash` 两列、**治不了缺行** → 该链永久 BROKEN。

**SQL 三铁证**（`ipd_dev.audit_logs` @18:44）：① 多行共享同一 `prev_hash`（16 行 seq1022-1037、15 行 1241-1255、13 行 812-824、11 行 1081-1091、9 行 673-681、9 行 859/861-868，全 `LOGIN_FAIL`）；② `LAG()` 算得 `link_breaks=484`、first=600、last=1264；③ 断裂点样本 seq 600/601/602/603 的 `got_prev` **全为 `d873f9a57c4c`**（同一值）而 `want_prev` 各不相同，605/606 全为 `2ddf1f753465`。并发写者身份已绑定：兄弟压测实例 `port=16040 jar=/tmp/ruoyi-admin-qa05p1.jar`，javap 证其含 `secondMillis=3`（DEF-4 毫秒修复在）、不含 `requireJson` → **断裂非旧 jar 遗留**。

**副作用推论（对既有断言的证明力否证）**：正因 seq 由 DB 赋值，「零跳号零重复」在无删行时**恒成立**，故对并发正确性**无证明力**；本设计的真实失败模式是**静默丢审计事件**（重试耗尽抛异常、`REQUIRES_NEW` 回滚）而非 seq 冲突。

**两个修复方向已备齐、未选型**（涉已冻结哈希协议 v1、共享库并发语义与 4 个在跑实例，且 `AuditLogService` javadoc L33 已预告长期方案为 QA-04 泳道 `audit_log_chain_heads`，归属与选型须由主协调器裁定）：
- **方向甲**（最小改动、不动协议）：去掉 `insertStrategy=NEVER`，让 uk 真参与冲突检测 → DEF-4 重试即刻生效；代价 = 高并发重试放大，「重试耗尽即丢审计」仍需兜底。
- **方向乙**（javadoc 已预告）：新增 `audit_log_chain_heads` 锚表做链头原子递增，seq 与 prev_hash 同一原子步取得，并发天然串行且无重试；代价 = 新表 + 迁移 + 须登记 `application.yml` 的 `tenant.excludes`。
