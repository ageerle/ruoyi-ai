## 4. 系统性反思：前后端功能完整性（本卡实测发现的四类结构性问题）

### ① 前端页49 完全未实现（前后端断层的典型）

后端 `POST /api/v1/handover/super-admin` 已就绪（confirmation 必填、语义完备），但前端（独立仓库）页49 对应界面不存在——确认短语输入框（原型按钮 disabled 直至输入与「确认移交管理员」一致）、准备度展示、历史移交记录页均无。**后端 Mock/单测绿 ≠ 业务闭环**：真用户当前无法通过 UI 完成移交。前端页归 DOC-09 Vue 工程排期，需在卡面登记「API 契约已定」供前端对齐：请求体 `{toPersonId, note, confirmation}`。

### ② 页49 原型契约四点对照（后端实现 vs 原型）

| 原型要素 | 状态 | 处置 |
|---|---|---|
| `confirmation` 确认短语（「确认移交管理员」） | ✅ 已实现 | 后端精确匹配强制校验，不依赖前端 disabled |
| `currentPassword`（原型 window.prompt 输当前密码） | ❌ 未实现 | **登记差异**：本系统 persons 无密码登录交互（passwordHash 字段在但无流程），会话凭证即身份证明；如后续引入密码体系须补 |
| `replacementLeadId`（接任人承接原产品组组长） | ❌ 未实现 | **登记增量**：属页49 完整复刻范围，归 P0-10.49/DOC-09 排期 |
| `readiness.checks` 准备度检查端点 | ❌ 未实现 | **登记增量**：前端可先自行预检（接手人存在/在职/非本人）；独立端点待前端页开工时一并定契约 |

### ③ 真库存量违反单超管不变式（探针实锤，须收敛）

真库 13306/ipd_dev `persons`：25 人全 ACTIVE，**在任 SUPER_ADMIN 有 3 名**（900101 ipd-admin、9110001 傅志谦、2096266884100935682 系统管理员）。页49 契约「系统始终只有一名活动超级管理员」在存量上不成立。原兄弟实现用 `LIMIT 1` 静默选一个超管做移交——其余超管不受影响，移交后不变式仍破。**本轮已加防御：多名在任超管时拒绝移交**（错误信息明示「须先收敛至一名再移交」+ 新测试 `multipleAdmins_rejected`）。**存量收敛本身是运维/数据治理动作，非本卡代码范围**→ 登记待办：与 owner 裁决保留哪一名（疑似 900101 ipd-admin 为种子账号），其余两名人工降级。

### ④ 旧会话失效机制查证闭环（不改 security 的依据）

`IpdAuthSession.currentPerson()` 每请求实查 `persons`；`IpdAuthService.scopeOf` 对 `DISABLED` 返回 `Scope.NONE`（default 分支）；`IpdPermission.requireInternal` 对 NONE 抛 401。因此旧超管被置 DISABLED 后，**旧 token 的下一个请求即 401**，无需依赖 `IpdAuthSession.revokeAll`（其注释自认「撤销尽力而为，靠 credentialMarker 兜底」，StpLogicJwtForSimple 无状态不可靠）。「完成后旧超管账号禁止登录」由既有基建闭环，本卡零 security 改动。
