## 1. 页面 → API 总览

| 页面行为 | API | 说明 |
|---|---|---|
| 进入 `/recruitments` 详情，`status=OPEN && invited` 时渲染应标编辑器 | `GET /api/v1/bid-invitations/{id}` | 拿招标单状态（OPEN/SELECTED/CLOSED/WITHDRAWN）与本人可见性 |
| 招募列表/我的被邀请列表 | `GET /api/v1/bid-invitations?...`（分页） | 候选 rd_pm 过滤 mode=ONE_TO_ONE + targetPersonId=本人 |
| 点「接受」提交应标 | `POST /api/v1/bid-responses`（body.decision=`accept`） | 密封应标，落库 PENDING |
| 点「拒绝」 | `POST /api/v1/bid-responses`（body.decision=`reject`） | **不留痕**：无业务行、无审计、无通知 |
| 撤回已提交应标 | `PUT /api/v1/bid-responses/{id}/withdraw` | 状态置 WITHDRAWN |
| 查看某招标单应标情况（发起人视角） | `GET /api/v1/bid-invitations/{id}/responses` | 密封性：仅发起人可看全量（见 §6） |

所有响应统一走 `ApiV1Response` 包络：`{code, message, data}`，`code=0` 成功。

## 2. 提交应标：`POST /api/v1/bid-responses`

### 2.1 请求体（JSON，`BidResponse` 形态）

| JSON 字段 | 类型 | 必填 | 校验（服务端） | spec 页21 对应 |
|---|---|---|---|---|
| `invitationId` | number | 是 | 不存在 → `50001` NOT_FOUND | `:id` 路径参数（见 §5 差异 D-1） |
| `decision` | string | 否 | `accept`\|`reject`；**null 默认 accept**；拼错值 → `10001` | `decision` |
| `responseNote` | string | accept 必填 | **40–500 字**（承载方案摘要）；超界 → `10001` | `solution_summary`（≥40 字） |
| `rdPmId` | number | — | **服务端权威**：以会话用户为准，请求体该字段被忽略 | —（不信任前端） |
| `id`/`status`/`respondedAt` | — | — | 响应字段，请求无需携带 | — |

### 2.2 响应语义

| decision | HTTP | code | data | 副作用 |
|---|---|---|---|---|
| `accept`（新建） | 200 | 0 | 应标行（status=`PENDING`） | 写 `bid_responses` + 审计 `bid_response`/`accept` |
| `accept`（重复提交） | 200 | 0 | 更新后的同一行 | **覆盖更新不产生第二行**（BR-REC-BID-03）；已中标(ACCEPTED)后再提交 → `50002` |
| `reject` | 200 | 0 | `null`（**204 语义**） | **零副作用**：不写业务表/不写审计/不通知（BR-TEAM-03 / AC-TEAM-03） |

前端处理要点：`reject` 成功的判定条件是 `code===0`，**不要**检查 `data` 非空；成功后本地直接把候选人卡片置「已拒绝」。

### 2.3 错误码表（前端分支依据）

| code | 常量 | HTTP | 触发条件 | spec 页21 原码 |
|---|---|---|---|---|
| `30001` | FORBIDDEN | 403 | ONE_TO_ONE 模式且会话用户 ≠ targetPersonId（不在邀请名单） | `30001`（同号直用） |
| `50002` | STATE_CONFLICT | 409 | 招标单 status≠OPEN（状态机非法）；或本人已中标(ACCEPTED)再应标 | `40001`（见 §5 差异 D-2） |
| `50001` | NOT_FOUND | 404 | invitationId 不存在 | — |
| `10001` | PARAM_INVALID | 400 | decision 非 accept/reject；responseNote 超 40–500 字界 | — |

## 3. 撤回：`PUT /api/v1/bid-responses/{id}/withdraw`

- 仅本人（rdPmId=会话用户）可撤回；非本人 → `30001`；不存在 → `50001`；状态机不允许 → `50002`。
- 成功 `code=0`，data=更新后行（status=`WITHDRAWN`）。撤回后可重新应标（覆盖语义下的新提交）。

## 4. 数据读取端点

- `GET /api/v1/bid-invitations/{id}` → 招标单详情（含 `status`、`mode`、`targetPersonId`、`deadline` 等）。
- `GET /api/v1/bid-invitations`（分页 IPage）→ 列表；前端过滤「我被邀请」：`mode=ONE_TO_ONE && targetPersonId=本人`。
- `GET /api/v1/bid-invitations/{id}/responses` → 该单应标行列表（发起人/管理员视角）。

## 6. 密封应标与状态机（UI 联动）

- **密封性（BR-REC-BID-01）**：accept 的方案仅发起人（及管理员）可见；候选 rd_pm 之间互不可见——`GET /bid-invitations/{id}/responses` 不对候选 rd_pm 开放全量数据，前端不要在候选端渲染他人应标。
- **状态机**：应标行 `PENDING → ACCEPTED`（中标，遴选回写）/ `REJECTED`（落选，遴选时批量）/ `WITHDRAWN`（本人撤回）。招标单 `OPEN → SELECTED/CLOSED/WITHDRAWN`。编辑器仅在 `invitation.status===OPEN && invited` 时渲染。
- **审计**：accept 写 `bid_response/accept`；reject 与 withdraw 按 BR-TEAM-03 语义最小化。

## 7. spec 验收剧本 → API 调用序列（联调用例）

1. 候选人填表（摘要≥40 字）→ `POST /bid-responses {invitationId, decision:"accept", responseNote}` → `code=0`，卡片变「已应标」。
2. 候选人点拒绝 → `POST /bid-responses {invitationId, decision:"reject"}` → `code=0 && data===null`，卡片变「已拒绝」，DB 无记录（验收时后端自查 `bid_responses` 计数不变）。
3. 重复应标同单 → 仍 `code=0`，返回同一行（version 语义：单行覆盖，非新增）。
4. status≠OPEN 时提交 → `50002`，前端弹「招募已关闭/已遴选」。
5. 未受邀（ONE_TO_ONE 非目标人）提交 → `30001`。
