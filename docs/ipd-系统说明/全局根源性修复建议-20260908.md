## 一、Gate 仲裁：不是一层 DDL 缺口，是三层叠加

### 1.1 三层缺口（全部真库/源码实证）

| # | 缺口 | 证据 | 后果 |
|---|------|------|------|
| ① | `gate_arbitrations.decision varchar(16) NOT NULL` | 真库 SHOW CREATE TABLE 实测（建表脚本 `docs/script/sql/update/2026-09-06-ipd-p254-sign-deadline-arbitration.sql` L19） | `decision IS NULL` 恒假，未裁态在 DDL 层被封死 |
| ② | `openArbitration`（GateReviewService.java L726-737）只写审计 + 发通知，**不 INSERT 待裁行**；`arbitrate`/`finalRuling` 提交时才 INSERT | 源码实证 | 即使①修好，无行可查，工作台仲裁卡依旧恒空 |
| ③ | KeyGateArbitrationAggregator.java L45 按 `gate.status='PENDING'` 过滤，而仲裁仅存在于 `REJECTED` gate（`requireArbitratable` L708-710 要求 REJECTED） | 源码实证 | 照抄 KeyGateAggregator 签署态过滤的复制粘贴错误 |

**为什么单测全绿、真活全空**：测试 mock 了 `decision=null` + `gate status=PENDING` 的组合——这个组合在真库语义下**不可能存在**（NOT NULL 列造不出 null 行；REJECTED gate 不会是 PENDING）。三层缺口全部被一条假数据掩盖。

### 1.2 业务规则基准（供修复对齐）

- 触发：当轮双 PM「先 APPROVE 后 REJECT」分歧自动发起（BR-GATE-06，开发说明书.md:220），**不是**按轮次触发（「3 轮组长列席/5 轮超管介入」是否决重发规则，易混淆）。
- 链条：双 PM 协商 → 双组长联合仲裁 → 超管终裁（三级兜底无第四级，D19 拍板）。
- 值域：APPROVE | REJECT，无「改期」；无期限规则（3 自然日是双签 BR-GATE-04 非仲裁）。
- 终裁不翻转 Gate 终态（AC-GATE-10）；审计事件链 GATE_ARBITRATION_OPEN → SETTLED/ESCALATED → GATE_FINAL_RULING 已实现。

### 1.3 修复方案对比（三选一，推荐方案 1）

| 方案 | 内容 | 优点 | 缺点/风险 |
|------|------|------|-----------|
| **1（推荐）** | decision 改 NULLable + openArbitration 预落组长待裁行 + 聚合器过滤 PENDING→REJECTED | 与 gate_reviews 现行范式**完全同构**（真库实测 gate_reviews 就是 `decision DEFAULT NULL` + 预建占位行 + IS NULL 查待办）；查询契约零改动；迁移单条 SQL 零回填（存量 3 行全非 NULL）；`UPDATE ... WHERE decision IS NULL` 借 uk 天然幂等 | 需同时改①②③三层，只改一层救不活 |
| 2 | 加独立 status 列（PENDING/DECIDED） | decision 值域纯净 | 引入 gate_reviews 没有的新范式；decision/status 双源表达同一状态机，有漂移空间；改动面大一档 |
| 3 | 不改表，哨兵值 decision='PENDING' | 无 DDL | 污染值域（列注释与 ARBITRATION_DECISIONS 校验均不含 PENDING）；`arbitrate` L503-506 查重 anyMatch 不看 decision，预落后组长一进来就被「已提交」挡死，须连改查重；仓内先例 GateCreationService 的 decision("PENDING") 占位在真库 29 行中 0 次出现——该先例本身未被真活走通 |

**方案 1 迁移 SQL 草案**（人工 apply，沿 docs/script/sql/update/ 惯例）：

```sql
-- 2026-09-08-ipd-ga-nullable-decision.sql
ALTER TABLE gate_arbitrations
  MODIFY COLUMN decision varchar(16) NULL COMMENT 'APPROVE|REJECT（NULL=待裁，开仲裁时预落行）';
-- 存量 3 行均非 NULL，无需回填
-- 提醒：新表 apply 后须核对表级 GRANT（历史教训：kpi_shared_confirms 漏 GRANT 致 UPDATE 塌缩 500）
```

**方案 1 代码改动面**（5 处）：
1. GateReviewService.openArbitration：`collectLeaders(gate)` 每位组长 INSERT 一条 decision=null 行（uk 幂等兜底）
2. GateReviewService.arbitrate：查重改为「本人存在 decision IS NULL 行 ⇒ UPDATE ... WHERE arbitrator_id=? AND decision IS NULL」；0 行受影响 ⇒ 抛「已提交」
3. maybeEscalateAfterArbitration 超管终裁**不预落行**（终裁是「任一超管」非指派，首期维持 GATE_FINAL_RULING_REQUEST 通知通道）
4. KeyGateArbitrationAggregator L45：`.eq(Gate::getStatus, GATE_PENDING)` → `"REJECTED"`
5. KeyGateArbitrationAggregatorTest：mock gate 改 REJECTED + 补真库 probe 用例

## 二、P1.5 缺表 4 类：原型实证推翻旧拍板

### 2.1 核心修正

ZK-IPD 原型（产品流程细化管理工具 2/server/）对 4 类**全部建了独立表且全部投递 workflow_tasks**：
- gate_waivers（db.mjs:434-439）— 阶段门禁豁免
- rd_replacements + rd_replacement_approvals 双表（closure.mjs:65-75）— 研发 PM 替换四步链
- product_retirements + products 扩 retired_at/retirement_locked（final-rules.mjs:108-113/137-138）— 产品退市
- multi_project_capacity_approvals（final-rules.mjs:119-124）— 多项目产能备案（含 E2E 测试 final-rules.test.mjs:102-110）

这推翻了两份既有文档的判断：
- WB-17-1-拍板4项建议-20260908.md §4 的「3 复用 1 建」举例与真实 4 类**对不上**（疑似占位示例）
- review-workbench-tasktype-contract-20260908.md 的「capacity_approval 建议删除枚举」被原型 E2E 测试**证伪**

真库复核：`%waiver%` / `%replacement%` / `%retire%` / `%capacity%` 全部 0 命中——4 类确无表，复用路线（乙）在现库上也要加字段（gate_reviews 无 WAIVE 决策位、products 无 RETIRED 状态），**并非零成本**。

## 三、系统性根源反思：三类病根，五个案例

### 病根一：事实源漂移（业务规则散在四层且互相冲突，无仲裁机制）

| 案例 | 冲突内容 |
|------|---------|
| 豁免审批链 | 前端壳「双签」 vs 原型表结构两级 vs 原型实现三签——三处打架 |
| 退役 vs 退市 | 前端枚举「退役评审」 vs 原型/spec「产品退市」 |
| capacity 语义 | 契约评审关联 BR-INC-13（升降级） vs 原型实义「多项目备案」——误判险些删枚举 |
| 工程合同位置 | DOC-01~06 业务权威**只存在于 `.codex/ipd-integration/` 快照**，主仓 docs 下无此目录——权威文档本体脱离主仓 |
| KPI 状态值域 | 设计文档写 DRAFT，实体/Service 实际 EDITING（WB-17-1 P1.4 已踩，以代码为准修） |

### 病根二：写入侧与查询侧语义不对偶（数据生命周期完整性不在验收标准里）

| 案例 | 冲突内容 |
|------|---------|
| gate_arbitrations | 「提交才落行」（P2-5.4 意见表语义）vs 工作台「分配即落行、IS NULL 查待办」（gate_reviews 语义）——同一仓两种语义无人对齐，Gate 仲裁卡因此恒空 |
| GateCreationService PENDING 哨兵 | 代码写了 decision("PENDING") 占位逻辑，真库 29 行 0 次出现——写入路径本身未被真活走通，无人发现 |
| launch_date confirmer=NULL | HTTP 验收发现真库存在 confirmer_id 为 NULL 的行——上游写入未防御必填责任人 |

### 病根三：mock 与真库约束脱钩（假绿的结构性来源）

| 案例 | 冲突内容 |
|------|---------|
| 仲裁三层缺口 | mock 造了 `decision=null + gate PENDING`——NOT NULL 列造不出 null、REJECTED gate 不会是 PENDING，**mock 数据本身违反 DDL/业务约束**，单测全绿业务死路 |
| P1.2 mock 盲区 | mock 不执行 WHERE 条件，查询条件漂移测不出（已用「SQL+Java 双保险」缓解，但双保险只防值域漂移，防不了「数据形态不可能存在」） |
| isBlocking 值域 | 契约写 '1'/'N'，真库实值 '0'/'1'（stage_sign 透传）——前端 `==='1'` 碰巧兼容，无测试覆盖该差异 |

### 三类病根的共同放大器

**「已实现」的判定止步于单测绿 + HTTP 通，不包含「数据生命周期两端对偶」与「mock 数据合法性」检查**。每张卡独立验收时都绿，跨卡组合时（工作台聚合 9 张表）才爆——WB-17-1 恰好是第一个把 9 个域的数据拉到同一查询面的卡，所以集中暴露。

## 四、根源性修复机制（4 条，防复发）

### 机制 1：17 类 taskType 数据源契约登记（防病根二）

每类一张契约卡，聚合器实现**必须引用登记值而非硬编码**：

```yaml
# docs/ipd-系统说明/workbench-tasktype-契约登记.yaml（示意）
key_gate_arbitration:
  table: gate_arbitrations
  write_timing: ALLOCATE   # ALLOCATE=分配即落行 / SUBMIT=提交才落行
  pending_expr: decision IS NULL      # 未办态表达（NULL/status值/哨兵）
  gate_status_filter: REJECTED        # 外层状态过滤
  due_field: ~          # 无期限
  owner_field: arbitrator_id
```

配套静态一致性测试（仿 IpdPermissionCatalogDriftTest 思路）：断言聚合器代码中的查询条件与登记值一致；登记值与实体注解/DDL 脚本一致。**新增一类任务 = 先登记契约再写聚合器**。

### 机制 2：DDL apply 后核验扩项（防病根一之 DDL 面）

扩展 `p1-ddl-apply-check.py` 清单：聚合器依赖的列约束（如 gate_arbitrations.decision 必须可 NULL）+ 表级 GRANT 四权 + 值域抽查（DISTINCT 实值 vs 契约值域）。**「SQL 已 apply」的判定从「表存在」升级为「约束与消费方语义匹配」**。

### 机制 3：mock 合法性规约（防病根三）

写入测试规约（可落 .claude/skills 或 CLAUDE.md）：
- mock 数据必须满足真库 DDL 约束（NOT NULL 列不得 mock null；值域外的哨兵不得出现）
- 「未办态」用例优先补真库 probe（HTTP 或 JDBC），纯 mock 用例须标注「未覆盖 DDL 合法性」
- 复制粘贴相邻聚合器时强制 diff 检查状态过滤条件（缺口③的直接教训）

### 机制 4：文档 SSOT 收敛（防病根一之文档面）

- 工程合同 DOC-01~06 从 `.codex/` 快照回迁主仓 `docs/ipd-系统说明/工程合同/`（权威文档必须活在主仓）
- 缺表 4 类业务规格以**原型源码为基准**单独成文（本文档 §2 即雏形），owner 拍板 14 问后升格为 spec 补充
- 设计文档写「状态值」时必须同时写「实体常量名」——KPI DRAFT/EDITING 漂移的直接防复发
